# The Planning Loop

Before `build-item` or `ultracode-build` ever touch your repository, a roadmap has to exist: a hierarchy of containers down to executable items, wired into a real `blocked_by`/`blocks` dependency graph, and dated so the timeline reads as a clean cascade. Five skills do that work — `plan`, `comprehend-plan`, `insert-story`, `insert-defect`, and `rationalize-gantt`.

All five are portable with essentially no setup: they resolve your organization's work types, statuses and priorities from DevStride at runtime. Four of them — `comprehend-plan`, `insert-story`, `insert-defect` and `rationalize-gantt` — read nothing at all from your repository's config file. `plan` is the one exception, and reads exactly two optional things from it: `hierarchyRoles.releaseUnit`, as a tie-breaker when your hierarchy makes the release boundary ambiguous, and the `release.*` settings, to judge how fast your development branch reaches production. Neither is required, and none of the five needs a repository to be present at all. And none of them writes code. If planning surfaces something that also needs building, that is a later [delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop) run against the item these skills created.

::alert{type="info" title="Roles, not one organization's names"}
These skills reason in three roles, resolved from *your* hierarchy at runtime rather than assumed: a **leaf** is an executable, roughly-one-day item (typically a Story or Defect); a **release unit** is the container whose completion cuts a release (typically an Epic); everything above is a **container**. Nothing assumes canonical spelling or a fixed depth — organizations really do have custom tiers and even typo'd type names, and the skills plan against what your organization actually has. Where this page says "Epic" or "Story", read the level in yours that plays that part.
::

::alert{type="danger" title="Every one of these skills talks to production"}
The DevStride MCP targets `api.devstride.com` directly — there is no draft or sandbox mode. Every `create_item`, `update_item`, `add_relationship` and `bulk_update_items` call on this page is a real, immediately user-visible write to a live roadmap. The skills that mutate data are built to stop and ask for explicit sign-off before they do; this page says exactly where.
::

## Skills at a glance

| Skill | Argument shape | Entry point or building block | Writes live data? |
|---|---|---|---|
| `plan` | `<parent-item> [description]` | Top-level entry point, run directly | Yes — after explicit sign-off |
| `comprehend-plan` | `<item> [focus question]` | Both — a standalone research tool **and** the first thing other skills call | No — strictly read-only |
| `insert-story` | `[parent-item] <description>` | Both — directly runnable **and** the capture path `build-item` uses for discovered work | Yes |
| `insert-defect` | `[parent-item] <description>` | Both — same dual role, for bugs | Yes |
| `rationalize-gantt` | `<plan-root>` | Both — direct entry point **and** `plan`'s final step | Yes — overwrites dates and edges |

## `plan`

Drives a full container → release-unit → leaf hierarchy into existence under a parent item. It is explicitly **not** a one-shot document generator — it is an interactive, loop-based discovery process. The payoff is a hierarchy specced deeply enough that `ultracode-build` can execute from it unattended, with every leaf wired into a real dependency chain so `build-item` can walk the whole thing end to end.

```
/devstride:plan <parent-item> [description]
```

`<parent-item>` is a container to plan under, optionally followed by a short description of what is being planned. Omitted, the skill asks rather than guessing.

**It grounds before it asks.** Its first move is to invoke `comprehend-plan` on the root and classify what it finds into exactly one of three states, stated out loud: an **empty root** (plan from scratch), a **partial plan to extend** (default posture is strictly additive — existing items are locked inputs, and touching one needs your explicit authorization), or **shallow placeholders** (items exist but were never really planned — it asks whether to flesh them out in place or replace them, because scaffolding is sometimes intentional). It never invents a rebuild.

**Safety and autonomy.** The Q&A, scope calls and architecture judgments always happen in the main conversation — never inside a fanned-out drafting agent. `plan` orchestrates its heavy drafting in parallel at maximum effort, but a drafting agent cannot pause to ask a question, so the split is strict: **humans decide, the fan-out only drafts**, and its output comes back as a proposal to review rather than a commit. If you try to skip the discovery loop ("just make something up", "you decide"), the skill pushes back once, explaining that a plan built without real answers looks structured but isn't buildable; if you still insist, it complies and labels every assumption as one. It requires an explicit "yes, build this" on the full shape before creating anything, plus a content review of the drafted specs before any write. It also folds one heads-up into that same sign-off: the final step needs your organization's dependency propagation turned **off**, which cannot be done through the API — so you are told during drafting rather than stalled at the tail of an otherwise unattended run.

### What it insists on about release units

The shape `plan` produces is not cosmetic — the release unit is the level the delivery loop branches at and releases from. Three shaping rules follow, and the skill asks the questions behind each:

- **A release unit must be a self-contained, shippable unit of end-consumer value.** The question it asks directly is: *if we shipped only this release unit and stopped, what can the end consumer now do that they couldn't before?* If the honest answer is "nothing yet", the boundary is wrong. Prefer vertical slices (schema → backend → frontend → the user can do something new) over horizontal technical layers that each ship nothing usable alone. Where foundation work genuinely must come first, fold it into the first value-delivering unit that needs it — or, if it truly fans out to several, mark it explicitly as an internal enabler so it is a deliberate exception rather than the norm.
- **A release unit must be independently production-safe wherever promotion is frequent.** If your development branch reaches production daily, there is no soak period and no later tidy-up window. So the plan asks, per release unit, what its **blast radius** is on day one (who is exposed, what flag or opt-in gates it, or explicitly nothing), whether it stands up anything **billable or externally visible** — an owner decision to raise during planning, not a footnote discovered in a bill — and whether it has any internal **deploy-ordering** hazard where one item references a resource another creates. Those answers are captured in the spec as an explicit *Release safety* section, so the delivery loop meets them at the release gate instead of rediscovering them.
- **Deferred work never parks under an active value release unit.** Follow-ups, tech debt and "we'll harden this later" items keep a unit from ever reaching zero remaining leaves, which means its release can never cut. The plan provisions a dedicated deferred-work release unit up front and parks them there, keeping their `blocked_by` edges pointed back at whatever produced them. A leaf whose theme doesn't match its release unit is a rehoming signal, not a naming problem.

### Depth is deliberately uneven

Containers get one terse paragraph. Release units get real architecture: an overview by subsystem naming likely files and services, the invariants the unit establishes, its release-safety section, what it feeds elsewhere in the plan, and a numbered delivery sequence of its own children. Leaves get an implementation-ready spec — data model with exact tables and columns, backend files and methods, explicit frontend scope (or an explicit "none in this item, that's a separate one"), permission keys and the invariant each enforces, the exact test file and its enumerated cases, structured dependency data, named edge cases recorded as *decisions* rather than oversights, and a concrete definition of done. Padding the container level to match is miscalibration, not thoroughness.

## `comprehend-plan`

Recursively reads a plan's descriptions **and** comments, at every level, to build a grounded picture of what a container actually holds, where it stands, and what its real — not just titled — intent is. Comments carry the as-built history and mid-flight decisions that descriptions rarely get updated to reflect, so a description-only pass doesn't count as comprehension.

```
/devstride:comprehend-plan <item> [focus question]
```

The focus question ("what's left before webhook intake is done?") sharpens the synthesis but never narrows what gets read.

**Both an entry point and a building block.** Run it standalone whenever the question is "what is the state of X". Other skills call it internally: `plan` invokes it first to classify the root before any discovery. Its own guidance says to use it before `insert-story`, `insert-defect`, `rationalize-gantt`, or any surgical edit to a plan you don't already carry full context on.

It fans the reading out in parallel over the tree and returns structured records per item rather than raw content, then synthesizes by hierarchy: real intent reconciled against comment history, where the plan stands, what `build-item` would pick up next, known deferrals and gaps. **A comment that contradicts or supersedes its item's description is reported as a live discrepancy**, not silently resolved in favour of one. On a very large tree it scopes to a sub-branch and tells you it did.

**Safety and autonomy.** Strictly read-only — it must never call a mutating tool, which is also why it needs no sign-off of its own; the caution belongs to whatever mutating skill consumes its output next. It reads more free-text, externally-authored content than any other skill in the system — every comment on every node — which makes it the **primary prompt-injection exposure**. Instructions embedded in a description or comment are treated as untrusted data, never acted on, and flagged in the report.

## `insert-story`

Inserts ONE new leaf into a live roadmap, spliced into the dependency chain so `build-item` picks it up next. Its position is made to look native to the plan; its description stays an honest spec of the real work — never a fabricated "this was always planned" backstory.

```
/devstride:insert-story [parent-item] <free-text description>
```

The parent container can prefix or suffix the description. Given only an item number, or nothing real to spec from, the skill stops and asks rather than inventing a ticket.

**Both an entry point and a building block.** Run it directly to add one more item to an existing plan. It is also the canonical capture path `build-item` uses **after** a merge and completion ritual, turning an untracked deferral surfaced during adversarial review into a tracked, dependency-ordered item. The build engine itself never calls it — it only compiles the list that the orchestrator acts on afterwards.

**How the splice actually works.** The skill identifies `NEXT` (what `build-item` would pick up next) and `UPSTREAM` (what `NEXT` was blocked by), then rewires: the new item becomes `blocked_by` `UPSTREAM`, the old `UPSTREAM → NEXT` edge is removed, and `NEXT` becomes `blocked_by` the new item. What removes the old next item from contention is **the splice itself**, not priority. Priority — resolved as your organization's own `priorityId`, never a comparable string — only matters against *other* candidates, and even then cannot out-rank a still-open container that starts earlier elsewhere in the plan, because selection sorts by container date first. So rather than assume the splice worked, the skill **re-derives what `build-item` would actually pick next** and tells you plainly if something else still wins.

::alert{type="warning" title="An edge-less item is not a harmless one"}
If nothing is currently selectable, the skill establishes *why* before falling back. A genuinely finished plan is fine: it attaches after the last completed item and takes a dotted number. But **open leaves that are none of them selectable is a stop** — wiring the new item to an unrelated completed item would make it independently eligible and paper over a blocked or cyclic plan. The reason this matters is a quiet failure mode: an item with no execution-order prefix and no dependency edges is exactly what the delivery loop's one-off heuristic matches, so it would be shipped **straight to your base branch**, bypassing the plan's integration branch entirely.
::

**Safety and autonomy.** Before wiring any edge it confirms your organization-wide dependency propagation is off (the same check `rationalize-gantt` uses) — adding an edge while it is on can silently overwrite live dates on downstream items — and it warns rather than wiring blind if it cannot confirm. It assigns the new item a dotted execution-order number that sorts strictly between its neighbours' and **never renumbers them**. It explicitly does **not** re-rationalize the rest of the plan's dates; that is a separate, deliberate `rationalize-gantt` call. And it runs no part of the build loop.

## `insert-defect`

Nearly identical to `insert-story`, but for bugs: it splices a new Defect into the chain with an honest repro and root-cause description instead of a feature spec, and it will file under the container that owns the broken behaviour even when that container is otherwise finished — reopening its slot is fine.

```
/devstride:insert-defect [parent-item] <free-text description>
```

Given no real repro (expected-vs-actual), it stops and asks before creating or splicing anything.

**Safety and autonomy.** Every guardrail from `insert-story` applies. One extra behaviour: a defect often needs to jump **ahead** of already-planned work because it is blocking something real. The skill is explicit that this is not a unilateral decision — it states the case for queue-jumping and gets your **explicit confirmation** before splicing the defect earlier than a plain "insert next" would, then numbers it to sort into the position you agreed.

::alert{type="info" title="insert-* is for planned work; create-* is for one-offs"}
`insert-story` and `insert-defect` splice new work **into an existing plan's dependency chain** so the delivery loop reaches it in order. Their one-off siblings, **`create-story`** and **`create-defect`**, are for inbound work that is not part of any sequenced plan — an ad-hoc ticket or bug. Those two create the item (asking where in the map and which board), assign it to you, and hand straight to `build-item`'s single-shot mode: no chain splice, no `[N]` numbering, no next-item selection. They live in [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop), not here.
::

## `rationalize-gantt`

Backfills synthetic one-item-per-day dates and rationalizes the dependency graph so the plan renders as a maximally compressed, gapless, fully valid cascade. It assumes every leaf takes exactly one day — the agent build pace — so the result is a **synthetic critical-path view, not a real-world forecast**.

```
/devstride:rationalize-gantt <plan-root>
```

`<plan-root>` is the item whose descendant tree is the plan, or a roadmap name. Empty invocation prompts for which plan.

**Both an entry point and a building block.** Run it directly whenever a plan's dates have drifted or never reflected the real graph. `plan` also invokes it as its final step, once the new hierarchy is wired with zero orphan leaves.

::alert{type="danger" title="Overwrites live dates — including completed items"}
The cascade **overwrites existing start and due dates across the whole tree**, including the real completion dates `build-item`'s ritual stamped on shipped items. It confirms with you up front whether to re-date completed items too or only not-done ones. When `plan` calls it on the extend path it is explicitly told "not-done only", precisely to protect those completion dates.
::

**Turning off dependency propagation comes first, and is non-negotiable.** DevStride has a single organization-wide **[Enable Link Mode](/planning-concepts-and-use-cases/project-planning-tools/gantt-charts/link-mode)** setting (Settings → Organization). While it is on, the backend forward-reschedules anything with a `blocked_by` edge and overwrites the dates this skill just wrote — it mutates stored data, not just a view. There is no API flag that suppresses it for a single call, and the skill will not change a global organization setting on your behalf just to run a planning pass. So it reads the current value, asks you to turn it off if needed, and then **verifies** by writing a probe date to a dependent item and reading it back before any mass write. It also omits the propagation override from every write it makes, since supplying it would re-enable exactly what was just disabled.

**Cycles stop the pass before a single date is written.** A dependency cycle makes the depth computation non-terminating, and `plan` relies on this skill to catch one — so it detects cycles first and stops. Crucially it names the *actual* cycle members rather than everything downstream of them: an innocent item feeding a mutual pair never clears either, so reporting the whole remainder would send you fixing the wrong edge. It reports the cycle path, proposes which edge to drop or repoint, and asks you to re-run — because a stopped pass wrote no dates at all, which is worse than the state it was called to fix.

**Red lines are decisions, not offsets.** Every invalid dependency gets reviewed and resolved as **REMOVE** (redundant — the real prerequisite is already captured at leaf level), **REPOINT** (the intent is real but too coarse — re-point at the specific foundational item inside the container), or a rare, deliberate **KEEP with an offset**, which de-compresses the timeline and is called out to you explicitly rather than applied silently. The two dominant sources of red lines are coarse container-level links and links to items outside the tree.

**It re-dates only.** Execution-order title prefixes are stable identifiers, so this skill writes dates and relationships and **never a title** — even when the recomputed cascade reorders items on the timeline. Prefixes disagreeing with date order is expected, because spliced items deliberately sit out of integer sequence.

## Execution-order numbers

`plan` stamps every leaf with a bracketed prefix — `[1] Add attachment table`, `[2] Add scan handler` — computed once the graph and dates are final, in the order the delivery loop will actually walk them. Whole integers mark the originally planned sequence; dotted numbers (`[23.1]`, `[23.1.1]`) mark items spliced in later.

They are **stable identifiers**. Nothing recomputes them: renumbering would churn shipped items and break every reference to them. A splice reads its neighbours' prefixes and picks one that sorts strictly between — `[23.1]` between `[23]` and `[24]`, `[23.2]` for the next insert into the same slot, `[23.1.1]` between `[23.1]` and `[23.2]`, `[40.1]` after the last item, `[0.1]` in front of the first. Plans authored before numbering existed are left alone rather than partially numbered; the skill says so and offers to number the whole tree in one pass.

## How they compose

### Planning something new from scratch

You run `/devstride:plan I20100` under the parent container. `plan` doesn't hand-roll a tree read — it invokes `comprehend-plan` on the root to learn what already exists. That classification is followed by a full multi-round discovery loop — source material, scope boundaries, container breakdown, release units per container, leaf shape, sequencing intent, risk areas — entirely in the conversation. The parallel fan-out opens only after you have signed off on the shape, purely for bulk drafting.

When it comes time to create, `plan` reuses the same call patterns `insert-story` and `insert-defect` use — same field shape, same today-dated placeholder — but explicitly **not** their insert-before splice topology. Those skills wire one item between an existing upstream and next; `plan` is building a whole fan-out/fan-in graph, so it owns that wiring itself, with a hard requirement that **every new leaf ends up with at least one edge — zero orphans**, verified rather than assumed. It creates every intermediate container tier your hierarchy requires, because a skipped tier is rejected by the backend *after* part of the tree already exists. Then it finishes by invoking `rationalize-gantt` to date the plan and clean up any invalid lines the new items introduced, and stamps the execution-order prefixes.

The graph it aims for is the shape real large plans take: mostly **wide fan-out and fan-in around a small number of narrow serial gate items** — a foundation item that blocks everything touching its subsystem, convergent items with several prerequisites, genuinely independent branches left parallel. Dependency *accuracy* is the goal, not a single serial thread.

### Splicing in one more item later

Once a plan exists, adding one newly discovered piece of work doesn't need a full `plan` pass. Running `insert-story` (or `insert-defect`) resolves the parent plan, identifies what the loop would currently pick up next and what it was blocked by, and splices the new item in between — leaving the rest of the plan's dates untouched. This is the same mechanism `build-item` invokes automatically, after a merge, when adversarial review turned up an untracked follow-up with no existing home. If the plan's dates genuinely need re-compressing around the new item afterwards, that is a separate, explicit `rationalize-gantt` call: insertion and date rationalization are deliberately two actions, not one.
