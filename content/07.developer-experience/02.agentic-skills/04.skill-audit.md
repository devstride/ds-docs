# Skill Audit: All Sixteen Skills

This is the flat reference for the `devstride` plugin's skills — one entry each, with **how you invoke it**, **the argument it takes**, and **what it does**. The two loop pages ([the planning loop](/developer-experience/agentic-skills/claude-skills-planning-loop) and [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop)) tell the *story* of how they chain together; this page is the index you scan when you just need to know what one skill is and how to call it.

Skills are namespaced by the plugin, so every one invokes as **`/devstride:<name>`** — bare verb names, no prefix on the skill itself. Claude Code can also pick one up automatically by name and description. Where it matters, a skill reads its repo-specific values from `.claude/ds-config.json` in the repository it is running in; see the [configuration reference](/developer-experience/agentic-skills/configuration-reference). If any of the terms below are unfamiliar, start with the [overview](/developer-experience/agentic-skills/claude-code-skills-overview) for the what, the why, and the shared safety model.

::alert{type="danger" title="Skills marked writes live data act on PRODUCTION"}
Those skills call the DevStride MCP at `api.devstride.com` — your real workspace, with no draft or sandbox mode. Every `create_item` / `update_item` / `add_relationship` lands immediately and is visible to your organization's real users. See the [safety model](/developer-experience/agentic-skills/claude-code-skills-overview#the-safety-model) for the full contract.
::

| [`pr`](#pr) | `[item-number]` | Open the pull request, run the review stack, optionally link it to its item |
| [`review`](#review) | `[PR#]` | **Review engine** — run every engine, triage, fix, reply-and-resolve, release CI, settle green |
| [`push`](#push) | *(none)* | Stage, commit with your conventions, type-check, and push (never opens a PR) |
| [`release`](#release) | `[no docs \| skip docs \| docs only]` | Promote the release branch to production: PR, gated review, docs pass, owner-gated merge |

Notation: `<required>`, `[optional]`, `a | b` are alternatives. `I####` is a DevStride item number; `F####` is a workstream/folder.

::alert{type="info" title="Container, release unit, leaf"}
The skills reason in **roles**, not in one organization's work-type names. A **leaf** is an executable, roughly-one-day item — a Story or Defect in a typical setup. A **release unit** is the container whose completion cuts a release — usually an Epic. Everything above that is a **container**. The roles are resolved from your own hierarchy at runtime (or pinned in `hierarchyRoles`), so a shallower or deeper hierarchy simply has fewer or more container tiers. Where this page says "Epic" or "Story", read the level in *your* organization that plays that part.
::

## Planning skills

Skills that shape the roadmap and its dependency graph, **before any code is written**. None of them touches your repository. Narrative: [the planning loop](/developer-experience/agentic-skills/claude-skills-planning-loop).

### `plan`

- **Invoke:** `/devstride:plan <parent-item> [description]` · **writes live data (after sign-off)**
- **Argument:** the container item to plan under (e.g. `I20100`), optionally followed by a short description of what is being planned. Empty → it asks which item rather than guessing.
- **What it does:** drives a full container → release-unit → leaf hierarchy into existence through an **interactive, loop-based discovery process** — explicitly not a one-shot generator. It comprehends what already exists first, classifies the root as empty / partial-extend / shallow-placeholder, asks scope, sequencing and risk questions in rounds, and only after an explicit "yes, build this" creates anything. Then it wires every leaf into a real `blocked_by`/`blocks` graph with **zero orphans**, calls `rationalize-gantt` to date that graph, and only *then* stamps the execution-order `[N]` title prefixes. That order is load-bearing rather than incidental: the numbers are the order the delivery loop will walk the plan in, and that order is not knowable until the graph is wired and dated — so dating comes first (step 6) and numbering last (step 6.5). Judgment calls always happen in the conversation; only bulk drafting is fanned out in parallel. It shapes each release unit as a self-contained, shippable increment — the same boundary `build-item` later branches and releases at — and insists on a dedicated home for deferred work so a value release unit can actually reach zero remaining items.

### `comprehend-plan`

- **Invoke:** `/devstride:comprehend-plan <item> [focus question]` · **read-only**
- **Argument:** the plan root to comprehend, optionally followed by a focus question such as `what's left before webhook intake is done?`. The question sharpens the synthesis but never narrows what gets read.
- **What it does:** recursively reads a plan's descriptions **and every comment**, at every level, to build a grounded picture of what a container actually holds and where it stands. Comments carry the as-built history that descriptions rarely get updated to reflect, so a description-only pass isn't comprehension — it's a title read. It reconciles the two and flags any comment that contradicts or supersedes its description as a live discrepancy rather than silently picking one. It mutates nothing; other skills call it first (`plan` step 1) to avoid clobbering an existing plan, and you run it standalone whenever a plan's state is unclear. Because it reads more externally-authored free text than any other skill, it is also the system's main prompt-injection exposure: embedded instructions in a description or comment are treated as untrusted data and reported, never acted on.

### `insert-story`

- **Invoke:** `/devstride:insert-story [parent-item] <description>` · **writes live data**
- **Argument:** free text describing the story, optionally anchored to a parent container — `I20100 add rate limiting to webhook intake`, or just the description when there's no ambiguity. Too thin to write an honest spec from → it stops and asks.
- **What it does:** splices **one** new Story into a live plan's dependency chain, positioned so `build-item` picks it up next, with an honest spec — never a fabricated "this was always planned" backstory. It confirms your organization-wide dependency propagation is off before wiring any edge, creates a housing container if the plan needs one, sets priority so the item wins its date tier, then rewires the chain: the new item becomes `blocked_by` the current upstream, and the item that *was* next becomes `blocked_by` the new one. Afterwards it **re-derives what `build-item` would actually pick next** rather than assuming the splice worked, and tells you plainly if some other earlier-dated container still wins. It assigns a dotted execution-order number (`[23.1]`) and never renumbers its neighbours. It does **not** re-date the rest of the plan — that is a separate `rationalize-gantt` call.

### `insert-defect`

- **Invoke:** `/devstride:insert-defect [parent-item] <description>` · **writes live data**
- **Argument:** same shape as `insert-story` — free text describing the bug, optionally anchored to a parent. No real repro (expected-vs-actual) → it stops and asks.
- **What it does:** nearly identical to `insert-story`, but for bugs, with an honest repro/root-cause description, and it will file under the container that owns the broken behaviour even if that container is otherwise finished. One extra behaviour: a defect often needs to jump **ahead** of already-planned work because it is blocking something real — the skill states the case and gets your **explicit confirmation** before queue-jumping, rather than silently reprioritizing your roadmap.

### `rationalize-gantt`

- **Invoke:** `/devstride:rationalize-gantt <plan-root>` · **writes live data (overwrites dates and edges)**
- **Argument:** the item whose descendant tree is the plan, or a roadmap name. Empty → it asks.
- **What it does:** backfills synthetic **one-item-per-day** dates and rationalizes the dependency graph so the timeline renders as a maximally compressed, gapless, fully valid cascade — a synthetic critical-path view, not a forecast. It **overwrites existing start/due dates across the tree**, so it confirms the scope up front (including whether completed items are in scope). It detects dependency **cycles first and stops before writing a single date**, naming the actual cycle members rather than the innocent nodes feeding them. It then treats every invalid-dependency "red line" as a decision — REMOVE a redundant edge, REPOINT a too-coarse one at the specific item it really depends on, or a rare deliberate KEEP with an offset, which de-compresses the timeline and is called out explicitly. It re-dates only: it never touches titles or execution-order numbers.

## The delivery loop

Skills that carry code from a selected item to merged-and-Done. Narrative: [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop).

### `build-item`

- **Invoke:** `/devstride:build-item <item | next | under I####>` · **writes live data (status moves, links, comments)**
- **Argument:** an item number; `next` or empty for the next unblocked item; or a plan root to scope selection (`next under I20100`, or `I20100` alone — a bare container is a *scope*, never something to build). An item that is not part of a sequenced plan is auto-detected as a one-off and built single-shot.
- **What it does:** the **orchestrator**. It runs the whole loop — select → mark In Progress → branch → build → review → merge → completion ritual → capture findings → sync → next — composing the skills below and owning only the DevStride glue. It is designed to run under `/loop`, pausing only at a genuine fork, and it renders a progress table at every step transition so a resumed session can tell where it is. **Per-release-unit integration branches are the default:** a leaf under a release unit is built on that unit's integration branch (created on its first story, reused after), and such a story runs in **fast develop mode** — no pull request of its own, settled by the local engines plus green local suites and merged locally. The cloud reviewers and CI are not skipped but **deferred** to the release PR, which is the only thing that reaches your base branch and is reviewed **full-diff** because it is the first cloud pass over that code. Two kinds of item go straight to the base branch instead, keeping the full per-story pull-request ritual because nothing follows them: an item with **no release-unit ancestor at all**, and **every one-off**. Those are separate rules, not one. A one-off is routed to the base branch **unconditionally, by explicit bypass** — never by reasoning that it has no release-unit ancestor, because it very often does: `create-story` and `create-defect` both offer a release unit as a parent, and without the bypass the general rule would strand that one-off on the unit's integration branch until an unrelated release cut. When the release unit hits zero remaining leaves it cuts that release PR automatically **only if `autoRelease` is enabled**; otherwise it reports the unit release-ready and stops.

### `create-story`

- **Invoke:** `/devstride:create-story <description>` · **writes live data**
- **Argument:** free text describing the work, optionally anchored to a parent item (`I####`) or workstream (`F####`). Too thin to write an honest one-paragraph spec from → it stops and asks rather than inventing a ticket.
- **What it does:** the one-off entry point for inbound work that **isn't** part of any plan. It asks where in the map the item belongs and which board it should be visible on, resolves the assignee (defaulting to you) and a sensible priority, creates the Story with a real spec, and then hands straight to `build-item`'s single-shot mode to deliver it once. No dependency splice, no `[N]` numbering, no next-item selection. Use `insert-story` instead when the work genuinely belongs in a sequenced plan's chain.

### `create-defect`

- **Invoke:** `/devstride:create-defect <description>` · **writes live data**
- **Argument:** free text describing the bug, optionally anchored to a parent. A vague fragment ("it's broken") → it stops and asks for repro steps and expected-vs-actual.
- **What it does:** the one-off sibling of `create-story`, for an inbound bug not in any plan. Same placement questions, filed under the container that owns the broken behaviour, flagged as a bug, then delivered single-shot through the same build loop. Use `insert-defect` when the bug belongs in a plan's chain.

### `branch-feature`

- **Invoke:** `/devstride:branch-feature <branch-name>` · git only
- **Argument:** a short branch-name suffix, typically `I<number>-<short-slug>`.
- **What it does:** the everyday branch-creation utility. It aborts on a dirty tree, syncs the working base (the integration branch when `build-item` passes one — the default for planned work — otherwise `baseBranch`), creates `<prefix>/<MM-DD-YY>/<suffix>`, and pushes with `-u`. If the working base is an integration branch that doesn't exist yet, it **stops** and says so rather than silently falling back to your base branch. Used both standalone and as `build-item`'s branch step.

### `branch-hotfix`

- **Invoke:** `/devstride:branch-hotfix <branch-name>` · git only, plus whatever local reset your repo needs
- **Argument:** a short branch-name suffix. The branch is named `<prefix>/hotfix/<MM-DD-YY>/<suffix>`.
- **What it does:** a standalone tool for genuine production emergencies — it branches off a **fresh copy of `hotfixBaseBranch`** so the fix is built against what is actually running, not against queued work. It aborts on a dirty tree and recommends stopping your dev server first. If your repository has a database reset/reseed or migration procedure that belongs with a production-based branch, it tells you to run it and asks rather than guessing what that procedure is. It opens no pull request (a fresh branch has nothing to compare) and points you at `pr` when the fix is ready. On a failure partway through it reports which step broke **and which branch you are now on**, rather than leaving you stranded on the production branch without saying so. `build-item` never calls it.

### `ultracode-build`

- **Invoke:** `/devstride:ultracode-build I#### <one-line goal/scope>` · git + parallel agents
- **Argument:** an item number plus a one-line scope. It assumes the branch already exists and the item is already In Progress.
- **What it does:** the **build engine** `build-item` invokes once a branch exists. Three phases. **UNDERSTAND** provisions readers proportional to the story — three core lenses (downstream contract, module structure, test plan) plus more only when warranted, skipped entirely for a genuinely trivial change, with "unsure" treated as substantive. It produces a concrete build plan and a buildable-now-vs-deferred scope line. **BUILD** is a tight loop of small increment → checks green → commit, obeying your `conventionsDoc`, committing often, keeping type-checks and the touched tests green, and committing regenerated artifacts separately from hand-written code. **ADVERSARIAL REVIEW** runs parallel finders over the hand-written diff (correctness, security, contract-match, tests/false-green, cleanup) then verifies each finding as CONFIRMED, PLAUSIBLE or REFUTED — fixing the first two, dropping the third rather than "fixing" code that was proved correct. It opens no pull request and merges nothing; it hands back a summary, a deferral line, a **deviations list**, and an **untracked-deferral list**.

### `pr`

- **Invoke:** `/devstride:pr [item-number]` · **writes live data (linking only)**
- **Argument:** an optional item number used when linking the pull request to its item.
- **What it does:** owns pull-request **creation** and **linking**. It authors the body from your configured section template (never `--fill`, and no AI-attribution text in a body), opens the PR **as a draft** when your repo holds CI on drafts, and **requests every configured cloud reviewer in the same call** so the cloud review overlaps the local engines — the single biggest wall-clock saving in the loop. Then it delegates all review and CI gating to `review`. It detects two shapes that are not its flow: a production release (handed to `release`) and an **epic release PR** (whose body leads with the release unit and lists its constituent items). It also owns the **pre-ship hold**: when at least one declared local suite both *selects* this pull request (its `when` filter fires) **and** *matches* it (its path globs hit the final diff), it tells `review` to settle the review but stop short of releasing CI, runs those suites against the final diff, and only then discharges the hold. A non-empty config alone is not enough — a repo can declare several suites while this pull request matches none, and holding for a step that will do nothing buys a pointless round trip. Standalone it asks which base branch to target and offers to link the item; driven by `build-item` the base is pre-answered and the **linking step is skipped entirely**, because that loop does its own linking in its completion ritual and doing it twice would double-own it.

### `review`

- **Invoke:** `/devstride:review [PR#]` · git + GitHub
- **Argument:** a pull request number; empty → the current branch's open PR.
- **What it does:** the review and CI-gating **engine**. It starts by **resolving the roster** from config plus live probes and announcing it, then launches every stream concurrently: Claude's adversarial pass (skipped only if the build engine already covered this exact diff), a local review CLI if one is configured, and every configured cloud reviewer. It polls **reviewers only** — while the PR is a draft nothing is running to poll — collects **both halves** of a cloud review (inline threads *and* the review body, including the collapsed low-confidence block), **verifies every finding against the real code**, and triages each into fix / dismiss-with-rationale / capture-out-of-scope / ask. It applies fixes via `push`, **replies to and resolves** every thread it addressed, distils any durable lesson into the repo's lessons store, and only then rebases, marks the PR **ready** — which is what releases CI — and settles it green, distinguishing flaky failures from real ones. It also runs in a **local-only mode** for fast develop mode: given a base ref rather than a PR, it runs the local engine alone and stops after triage. The exact GitHub API procedures live in the skill's own reference files, loaded only when a step needs them.

### `push`

- **Invoke:** `/devstride:push` · git only
- **Argument:** none.
- **What it does:** a small git utility. It stages tracked changes with `git add -u`, then **adds any new file the change requires by name** — never a blanket `git add .`, which would sweep in unrelated untracked files, and never omitting new files, which would push a silently incomplete change while reporting success. It commits using your configured conventions (adding an item tag only when the work actually has an item — it never composes a number to satisfy a format), runs your type-checks, and pushes, falling back to `--force-with-lease` — never a bare `--force`, and never onto a protected branch — on a non-fast-forward rejection. A type-check failure that isn't a tolerated generated-file error **blocks the push**; it reports and asks. It never opens a pull request; it is the building block `review` calls to land fixes, and is equally usable on its own.

### `release`

- **Invoke:** `/devstride:release [no docs | skip docs | docs only]` · **writes live data + production deploy**
- **Argument:** optional. `no docs` / `skip docs` suppresses the documentation phase; `docs only` runs the docs pass against an already-shipped release without cutting or merging anything.
- **What it does:** promotes your release source branch to your production branch — the merge that triggers your deploy. It computes the release delta from the first-parent log and the merged pull requests in range, separating **user-facing** changes from internal ones, cuts the release PR (as a draft, with every cloud reviewer requested), and runs the full gated review scoped to the release surface rather than re-reviewing already-approved code. It runs your release-only pre-ship suites **unconditionally** — paths are deliberately ignored at the production boundary — and never describes one as "covered by CI" when it isn't. By default it then reviews and updates a sibling documentation repository, writing a release note when the delta is large and user-facing, discovering that repo's structure from the repo itself rather than hardcoding it. Finally it presents everything — review tally, each pre-ship result, the docs outcome, and a quoted reminder of what merging triggers — and **stops for an explicit go-ahead**. Invoking it is intent to prepare a release, never authorization to deploy one.

## Repo configuration and portability

Every concrete value these skills cite — branches, verify commands, generated-file paths, review engines, release settings — is externalized to a single file in the consuming repository, **`.claude/ds-config.json`**, which they treat as authoritative over any literal printed inline.

The planning skills are very nearly independent of it: `comprehend-plan`, `insert-story`, `insert-defect` and `rationalize-gantt` read nothing from it at all, resolving org configuration through DevStride at runtime. `plan` reads exactly two things, both optional — `hierarchyRoles.releaseUnit`, as a tie-breaker when your hierarchy makes the release boundary ambiguous, and the `release.*` branch/deploy settings, to judge how fast your development branch reaches production and therefore how strictly each release unit has to be independently production-safe. Neither is required, and planning runs fine against a repo with no config file, or with no repository in sight.

The practical consequence is that adopting the delivery loop in a new repository is **writing a config file**, not editing skills. See the [configuration reference](/developer-experience/agentic-skills/configuration-reference) for every key, and the [delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop) for what each one changes about how work ships.

::alert{type="note" title="Some skills belong in your repo, not in the plugin"}
The plugin carries only what generalizes. Tooling that knows your fixture generator, your database dump layout, or the internal reasoning behind your own conventions cannot travel — that belongs in your repository's own `.claude/skills/`, alongside the plugin rather than inside it. The split is the pattern: **plugin for the shared loop, local skills for your own ops.**
::

## Diagnostics

### `setup`

**Invoke:** `/devstride:setup [ecosystem \| verify \| ci \| branches \| engines \| docs]` — no argument runs the whole thing. A named detector inspects and reports only that part, and **writes nothing**.

The guided way to get `.claude/ds-config.json`. It inspects your repository for everything answerable without asking — package manager, verify commands, CI provider and whether its draft gating works, branch roles, which review engines you actually have, your conventions doc — reports each value with the evidence behind it, then reads your DevStride organization and asks which work types fill the release-unit and leaf roles.

It asks only about what it could not settle, confirming everything it could in one pass. **It writes exactly one file** and nothing else — not your code, not `CLAUDE.md`, not your workflows.

Then it executes what it wrote: your verify commands actually run, your branches actually resolve, declared engines actually respond. Only a run with zero failures calls the repository loop-ready. Tests are offered rather than forced, and skipped is reported as skipped, never folded into a pass.

Re-run it whenever the repository changes shape. A re-run proposes only what would change and merges, preserving hand edits, `_`-prefixed annotations, and keys it does not recognize.

Full walkthrough: [Guided setup](/developer-experience/agentic-skills/setup-guide).

### `doctor`

**Invoke:** `/devstride:doctor [env \| plugin \| devstride \| config \| ci \| gates]` — no argument checks everything.

**Read-only.** It inspects and reports; it never installs, writes config, edits a workflow, mutates git, or touches DevStride. That is what makes it the safe first thing to run, before you have committed to anything.

It exists because **every prerequisite of this loop fails silently.** A missing or unauthenticated `gh` surfaces as a failure part-way through your first pull request. A DevStride connection you never signed in to surfaces as *"I can't find any DevStride tools"* — not an authorization error, and nothing prompts you. A typo in `ds-config.json` surfaces as nothing at all: the key reads as absent and the skill quietly improvises. Workflows missing `ready_for_review` mean the ready-flip creates no run and the loop waits forever.

It walks six groups — environment, plugin install, DevStride connection, config file, the CI draft gate, and the merge gates — and reports each check as pass, fail or not-applicable. Every failure carries three things: what is wrong, **what it breaks**, and the exact command or edit that fixes it. It reports all of them rather than stopping at the first, so three problems cost one run.

Run it after installing, after editing your config, and any time the loop does something you did not expect.
