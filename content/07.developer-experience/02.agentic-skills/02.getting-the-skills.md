# Getting the Skills

Everything else in this section describes what the skills *do*. This page is how you get them onto your machine and keep them current.

It is short, but read it in order. Three of the steps below fail **silently** — nothing errors, nothing prompts, and the symptom looks like something else entirely — which is the only reason they are spelled out at this length.

::alert{type="warning" title="What this assumes about your setup"}
The planning half needs only a DevStride organization. **The delivery half is built on a specific stack, and it is not optional** — no part of it is configurable to something else:

- **git**, with a remote named **`origin`** that you can push to. The name matters: the delivery skills address it literally (`git push -u origin`, `git fetch origin`), so a fork checkout whose remotes are `upstream` and `fork` satisfies a casual "do I have a remote?" check and then fails at the loop's first push. Check with `git remote get-url origin`.
- **GitHub**, and **GitHub Actions** as your CI. The loop's whole review-then-CI ordering is implemented with GitHub draft pull requests and workflow job conditions. **Other forges are not supported** — GitLab, Bitbucket, Gitea and self-hosted alternatives will not work, and there is no adapter or configuration key that makes them work. If that is your setup, the planning half still runs standalone; the delivery half does not.
- **An authenticated GitHub CLI (`gh`)** with **write** access to the repository. A default read-only token is not enough: the skills open pull requests, push commits, request reviewers, **reply to and resolve review threads**, add labels, mark pull requests ready for review, and merge. Practically, that means a token carrying the `repo` scope (plus `read:org` for a repository owned by an organization). Check with `gh auth status`, and widen with `gh auth refresh -s repo,read:org` if it is short. If you also intend to let the loop change files under `.github/workflows/`, add the `workflow` scope.
- **A DevStride organization**, and an account in it with the access you expect the skills to use.

Two things it does **not** require: any particular language, package manager or test runner — you name your own commands in the config file — and any hosted service beyond the two above.
::

## 1. Access

The skills ship as a public Claude Code plugin:

| | |
|---|---|
| **Source** | [`github.com/devstride/claude-plugin`](https://github.com/devstride/claude-plugin) |
| **Licence** | MIT |
| **Contents** | Sixteen skills, invoked as `/devstride:<name>`, plus a bundled DevStride MCP server |
| **Price** | Free. It is a public repository, MIT-licensed, and the marketplace source is that repository. There is no licence to buy, no private registry, and no token to obtain. |
| **What it costs to run** | Model usage, and a lot of it — see below. |

Pull requests and issues against the repository are welcome; it is where the skills themselves live.

::alert{type="info" title="Free to install is not free to run"}
The plugin costs nothing. **Running it is deliberately model-usage-heavy**, and that is a design decision rather than an inefficiency: the build engine fans out parallel readers to understand a change before writing code, and *every* item gets a full adversarial review at maximum effort — there is no trivial-diff shortcut anywhere in the loop. A single item can therefore consume a large multiple of what one ordinary coding turn would.

It also takes real wall-clock time. One item means understanding, building, at least one adversarial pass, your local suites, and — on the pull-request path — waiting on cloud reviewers and CI.

So: **run one item before you ever reach for `/loop`.** Watch what a single `/devstride:build-item` actually does end to end, see what it costs you and how long it takes, and only then decide whether to let it walk a whole plan unattended.
::

**What you need before you start:**

- **Claude Code**, recent enough to have the plugin commands (`/plugin`, `claude plugin list`).
- **A DevStride organization**, and an account in it with the access you expect the skills to use. Signing in grants the skills exactly the permissions you already have — no more, and no sandbox.
- **A repository** you want the loop to work in, on **GitHub**, with an authenticated `gh` that has write access. The delivery half runs against real git branches, real pull requests and real workflow runs. The planning half needs no repository at all. See the assumptions box above for the full list, including which `gh` scopes the delivery skills actually need.

## 2. Install

### Add the marketplace and install the plugin

```
/plugin marketplace add devstride/claude-plugin
/plugin install devstride@devstride
```

Confirm it worked before going further — type `/devstride:` in the command picker and you should see seventeen skills, or run:

```bash
claude plugin list
```

That also shows the installed **version**, which matters later.

### Connect to DevStride

The plugin **bundles the DevStride MCP server**, so there is nothing to configure — no environment variables, no URL, no key. There is exactly one thing to do:

```
/mcp
```

Connect the server listed as **`plugin:devstride:devstride`**. Your browser opens, you sign in to DevStride, you pick an organization, and you are done. Installing the plugin never asks for a credential and never stores one.

::alert{type="danger" title="Signing in grants read AND WRITE access to the organization you choose"}
It grants exactly the access you already have in the DevStride app — creating, updating and deleting items included. There is no sandbox, no dry-run, and no narrower scope on offer: these skills write to live data by design. Read the consent screen before accepting, and pick the organization deliberately. See [the safety model](/developer-experience/agentic-skills/claude-code-skills-overview) for what the skills do with that access.
::

::alert{type="warning" title="Until you connect, the skills have NO DevStride tools — and nothing tells you"}
This is the first silent failure. Until you sign in, the server contributes **no tools at all** — DevStride rejects unauthenticated requests including the tool listing — and **nothing prompts you**. So the symptom is not an authentication error. It is a skill reporting that it cannot find DevStride tools, which reads like a broken install or a missing dependency.

That is the signed-out symptom. Connect the server and it goes away. (An *authorization* error is a different thing entirely, and means an expired session or a wrong key.)
::

For what the server itself exposes and how it behaves once connected, see [the DevStride MCP server docs](/integrations-and-extensibility/devstride-mcp-server/what-is-the-devstride-mcp-server).

Two more things worth knowing straight away:

- **A plain `devstride` entry in `/mcp` is not this server.** That is one you or your project configured separately. The bundled one always carries the `plugin:` prefix. If both are signed in they expose identically-named tools and the skills — which call tools by bare name — cannot tell them apart, which is how work meant for one organization lands in another. **Keep exactly one signed in.**
- **Your sign-in is bound to the one organization you picked.** There is no in-session switch. To move to another, run `claude mcp logout plugin:devstride:devstride` and connect again.

::alert{type="note" title="No browser? Use API-key headers instead"}
Browser sign-in needs a browser. Where there isn't one — CI, a container, an unattended agent — add your **own** MCP server with an API key generated under **Profile Settings → API Keys**, passing `X-DevStride-Api-Key`, `X-DevStride-Api-Secret` and `X-DevStride-Organization-Id` as headers via `claude mcp add --transport http`. The plugin's [README](https://github.com/devstride/claude-plugin) has the exact command. Prefer that over hand-writing a project `.mcp.json`: project-scoped servers need interactive approval before they connect, which is precisely what an unattended environment cannot give. And keep the credentials in environment variables — MCP config files are routinely committed.
::

### Rolling it out to a team

You can declare the marketplace and enable the plugin for a whole repository by committing `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "devstride": { "source": { "source": "github", "repo": "devstride/claude-plugin" } }
  },
  "enabledPlugins": { "devstride@devstride": true }
}
```

::alert{type="warning" title="That registers and enables the plugin — it does NOT install it"}
The second silent failure, and the one most likely to bite a team. A colleague who clones the repository gets the settings file and **no skills at all**, with nothing on screen explaining why. Every person still runs this once, on each machine they use:

```bash
claude plugin install devstride@devstride
```

Put that line in your onboarding notes rather than assuming the committed settings cover it.
::

Two adjacent traps come with the team path:

- **The `.gitignore` trap.** Many repositories exclude `.claude/`. If yours does, `.claude/settings.json` needs an explicit exception (`!.claude/settings.json`) or it will never be committed — and the rollout you think you shipped does not exist in the repository. The same applies to `.claude/ds-config.json`, and to the lessons store if you configure one.
- **Version drift.** An installed plugin stays on its version until someone updates it, so teammates who installed at different times can be running different revisions of the loop with nothing in the repository saying so. If a skill behaves differently for one person than another, compare `claude plugin list` versions before debugging anything else.

## 3. Update

**Updates are not automatic by default.** An installed plugin stays exactly where it is until you either opt in per marketplace, or ask for the new version explicitly.

**Once, to stop thinking about it:** open `/plugin`, select the devstride marketplace, and choose **Enable auto-update**. Claude Code then refreshes the marketplace and its installed plugins for you.

**Otherwise, per release — two commands, and both are required:**

```bash
claude plugin marketplace update devstride   # refresh the catalog
claude plugin update devstride@devstride     # upgrade the installed plugin
```

Then **restart Claude Code** to apply it.

::alert{type="danger" title="Running only the first command reports success and changes nothing"}
The third silent failure, and the most consequential one. `marketplace update` refreshes catalog metadata and prints a success message while leaving your installed copy exactly where it was. Everything looks like it worked.

This is the single most likely reason to conclude that a fix "did not ship" when it shipped days ago. If a behaviour you expected is missing, run **both** commands, restart, and check `claude plugin list` before reporting anything.
::

Two smaller mistakes in the same commands:

- **The update command needs the fully-qualified name.** `claude plugin update devstride` fails with "Plugin not found"; it must be `devstride@devstride`.
- **It acts on the `user` scope by default.** If you installed with `--scope project` or `--scope local`, pass the same `--scope` to `update` — otherwise it reports that the plugin is not installed and changes nothing. (`update` also accepts `--scope managed`, for a plugin an administrator installed for you; `install` does not offer that scope, so it is not one you can have chosen yourself.)

### Pinning to a release

Every release is tagged, so any version in the [changelog](https://github.com/devstride/claude-plugin/blob/main/CHANGELOG.md) can be held still. You pin by appending the tag to the marketplace **source** — there is no `--ref` flag, the ref goes in the source itself:

```bash
claude plugin marketplace remove devstride
claude plugin marketplace add devstride/claude-plugin@devstride--v<version>
claude plugin install devstride@devstride
```

Unpinning is the same three commands with the bare `devstride/claude-plugin` as the source. Restart afterwards either way.

::alert{type="warning" title="marketplace remove also uninstalls every plugin that came from it"}
Re-adding the marketplace does **not** bring them back — which is why the third line above is required, not optional. Skip it and you are left with a registered marketplace and no skills, and nothing says why. Any remove/re-add recipe you write down needs that reinstall step in it.
::

### What a version number promises

An existing skill name (`/devstride:<name>`) and an existing `.claude/ds-config.json` key keep working, and keep meaning the same thing, until a **major** version bump. New skills, new config keys, and changed skill behaviour arrive in minor bumps; wording fixes in patch. The plugin's [RELEASING.md](https://github.com/devstride/claude-plugin/blob/main/RELEASING.md) is the authority on that promise and on how releases are cut; the [changelog](https://github.com/devstride/claude-plugin/blob/main/CHANGELOG.md) records what changed in each one.

## 4. Point it at your repository

Installed and connected, the skills work — but they do not yet know anything about *your* repository. That comes from one file you write, `.claude/ds-config.json`:

```json
{
  "baseBranch": "develop",
  "protectedBranches": ["develop", "master"],
  "conventionsDoc": "AGENTS.md",

  "verify": {
    "typecheck": ["pnpm check:ts"],
    "test": "pnpm test",
    "testSingle": "pnpm test -- <path/to/test.spec.ts>",
    "lint": "pnpm lint"
  },

  "review": {
    "localCommand": null,
    "automatedReviewers": [],
    "openPullRequestsAsDraft": true
  }
}
```

Every key is optional and every key has a shipped default, so the loop runs before you write any of this — the file is how you adapt it to your repository, and **where it disagrees with a default, the file wins**. The highest-value key is `conventionsDoc`: point it at your coding-standards file and the build engine reads and obeys it, which is most of what makes the loop write code that looks like yours. Every other key is in the [configuration reference](/developer-experience/agentic-skills/configuration-reference).

::alert{type="warning" title="What that starter config leaves ON: most items get no pull request"}
It says nothing about `epicIntegrationBranches`, which means that block stays at its defaults — and its defaults are **on**. So on your first real run, an item that sits under a release unit will be built on that unit's integration branch, reviewed by the local engines, verified against your local suites, and **merged locally with no pull request of its own**. Only the completed release unit reaches your base branch, as one fully-reviewed pull request. That is the intended shape and [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop) explains why, but it is a surprise if you were watching GitHub for a pull request that is never going to appear.

While you are learning the loop, add this and every item goes through its own pull request and CI instead:

```json
"epicIntegrationBranches": { "enabled": false }
```

Take it out when the batching behaviour is what you want.
::

::alert{type="success" title="Or let setup write it for you"}
You do not have to write this by hand. **`/devstride:setup`** inspects your repository, works out most of these keys from what it finds, asks only about what it could not, writes the file, and then executes it to prove the values are right. Re-running it later merges rather than overwrites. See **[Guided setup](/developer-experience/agentic-skills/setup-guide)**.

The block above stays useful either way: it is what a minimal working file looks like, and it is the fastest path if you would rather start from a template than answer questions.
::

## 5. Gate your CI on the draft condition

**This is a change in *your* repository, not in the plugin, and skipping it fails silently.**

The loop's headline efficiency property is that every review engine settles before CI runs, and CI then runs exactly **once**, on the final reviewed diff. The mechanism is simple: `pr` opens every pull request as a **draft**, and `review` marking it ready is the deliberate act that releases CI.

That only works if your workflow jobs actually decline to run on a draft. Nothing in the plugin can do this for you — a workflow's trigger conditions live in your repository. **There are two parts, and the first one catches almost everybody.**

**First, listen for the flip.** GitHub's default `pull_request` event types are `opened`, `synchronize` and `reopened` — **`ready_for_review` is not among them.** So a workflow with a perfect draft condition and default types creates *no workflow run at all* when the loop marks a pull request ready. The condition never even gets evaluated, and the loop waits indefinitely for a run that will never exist:

```yaml
on:
  pull_request:
    types: [opened, synchronize, reopened, ready_for_review]
```

**Then decline to run while it is a draft** — on every job in that workflow:

```yaml
jobs:
  test:
    if: github.event.pull_request.draft == false
    runs-on: ubuntu-latest
    steps:
      # ...
```

A job that gates one cheap job and fans the result out through `needs:` is already covered — a skipped dependency skips its dependents, so those jobs need no condition of their own. And a workflow triggered by `pull_request_review` rather than `pull_request` should *not* be gated: it needs to run on drafts.

Then tell the config where those workflows live, so the skills can reason about them:

```json
"ci": {
  "workflowGlobs": [".github/workflows/*.yml"],
  "draftGateCondition": "github.event.pull_request.draft == false"
}
```

**`/devstride:doctor` checks both parts** and reports which workflows and jobs are missing them — worth running once after you make this change. Miss this and nothing errors. CI simply fires the moment each pull request opens, runs again after every review-fix push, and you pay for the slow half of your pipeline several times over per item — while the documentation tells you it runs once. The `draftGateCondition` key is *descriptive*: it records what your workflows do, it does not impose it.

::alert{type="note" title="A cheap way to prove the gate opened"}
Once the gate is in place, name a fast, path-filter-free job in `ci.gateJobName`. The skills then use its conclusion as proof that the ready-flip genuinely released CI. The failure it catches is otherwise invisible: a flip that lands too soon after a push can leave every job reporting `skipping`, which renders identically to a suite being legitimately non-applicable — a skipped board read as a green one is a merge with no CI behind it.
::

## 6. Try it safely, before anything writes

Two skills are **strictly read-only**, and between them they answer the two questions you have at this point: *is my setup right?* and *can it actually reach my organization?*

**Start with the setup check.** It never changes anything, and it tells you what is missing rather than leaving you to infer it from a later failure:

```
/devstride:doctor
```

It walks your environment, the plugin install, the DevStride connection, your config file, the CI draft gate and the merge gates, and reports each as pass, fail or not-applicable — every failure with what it breaks and the command that fixes it. Run it now, and again after any change to `.claude/ds-config.json`.

**Then prove the connection end to end.** `comprehend-plan` also never calls a mutating tool, which makes it the right first command to run against real data — it proves the plugin is installed, the MCP is connected and your organization is reachable, without changing a single thing.

```
/devstride:comprehend-plan I1234
```

Point it at any item you already have. It reads that item and everything beneath it — descriptions *and* every comment — and reports what the plan holds and where it stands. If it comes back with a real summary, your install and connection are both good. If it reports that it cannot find DevStride tools, you have not connected the MCP server yet; go back to step 2.

**What is and is not reversible.** Worth knowing before you run anything that writes:

- **Items can be deleted or archived in the DevStride app.** If a planning run creates a hierarchy you do not want, you can remove it by hand. Tedious for a large plan, but recoverable.
- **Statuses, descriptions and relationships can be edited back.** A status move to In Progress, a rewritten description, a dependency edge — all of these are ordinary changes you can undo in the app.
- **Dates overwritten by `rationalize-gantt` cannot be recovered.** It rewrites start and due dates across the whole tree, and the previous values are simply gone — there is no undo and no history to restore them from. That includes real completion dates a previous delivery run stamped on shipped items, which is exactly why the skill asks up front whether completed items are in scope. Answer that question deliberately.
- **Code changes go through git**, so they carry the usual safety net: a branch, a diff, review, and a history you can revert. The item side has no equivalent, which is why the skills that touch items ask before writing.

## 7. Then plan something and build it

```
/devstride:plan I1234
```

Pass the item you want to plan **under** — a *container*, meaning any item in your organization's hierarchy that holds other items rather than being a unit of work itself. In a typical setup that is a Solution, a Capability or an Epic, not a Story.

**Where do you find that number?** Open the item in the DevStride app; its number is shown on the item itself and in the URL, in the form `I1234`. Any item you can navigate to will do — the skills look the number up rather than composing one, so a wrong number fails cleanly rather than writing somewhere unexpected.

**What if your organization is empty?** Then there is nothing to plan under yet, and `plan` will tell you so. Create one container item in the app first — the highest level your hierarchy offers, named for the initiative you are about to plan — and pass that. `plan` builds the whole structure beneath it; it does not create its own root.

The command opens an interactive discovery loop, not a document generator: it asks about scope, sequencing and trade-offs, and **creates nothing** until you have signed off on the shape.

Then build the first item of what you planned:

```
/devstride:build-item
```

That selects the next unblocked item, marks it In Progress, branches, builds, reviews, merges, and updates the item — once, then stops. **Run it exactly this way the first few times.** When you are satisfied with what one pass does, you can hand it to `/loop`:

```
/loop /devstride:build-item
```

`/loop` is **Claude Code's own repeat mechanism**, not part of this plugin and not aware of DevStride: it simply re-runs the command that follows it until you stop it, which here means walking the plan item after item. **To stop it, press `Esc`** to interrupt, or say "stop looping". Given what a single item costs in model usage and wall-clock time, do not start here.
