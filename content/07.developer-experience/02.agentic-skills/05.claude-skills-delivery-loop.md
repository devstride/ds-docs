# The Delivery Loop

The delivery loop carries ONE tracked item from "next unblocked" to "merged and Done" — branching, building, self-reviewing, addressing findings, merging, running the completion ritual — then loops to the next one. `build-item` is the orchestrator; `branch-feature`, `ultracode-build` and `pr` are what it composes directly. Beneath `pr` sits **`review`**, the single review-and-CI-gating engine, and `push` is the git utility nested deepest, called to land fixes. `release` sits above all of it, promoting finished work to production. Every one of these is usable on its own as well.

Two things decide the *shape* of a run before anything else happens. **Where an item sits in your hierarchy** decides its working base — a release unit's integration branch, or your plain base branch — and that in turn decides whether the item gets a pull request of its own at all. And where your config holds CI on drafts (`review.openPullRequestsAsDraft`, on by default), **any pull request the loop does open opens as a draft**, which holds CI until the review engines have settled; the ready-flip is what releases it, so CI runs once, on the final reviewed diff.

::alert{type="danger" title="The DevStride MCP writes to PRODUCTION"}
`get_item`, `update_item`, `add_comment` and `link_pull_request` act on your real, live workspace at `api.devstride.com`. Every status move `build-item` makes — In Progress at the start, Done at the end — and every link or comment is a real, user-visible change to a live item, made the instant it runs. The MCP cannot exercise branch code, so there is no way to "hold" an item write until the code ships; the write simply happens.
::

## `build-item` — the orchestrator

```
/devstride:build-item <item | next | under I####>
```

It runs the whole loop: **select → mark In Progress → branch → build → review → merge → completion ritual → capture findings → sync → next — and, when a release unit's last item lands, the release to your base branch.** It composes the other skills by name and owns only the DevStride glue: selection, status transitions, the completion ritual, the release. It is designed to run under `/loop` for full autonomy.

A bare container number is a **scope**, not something to build — `I20100` alone means "the next unblocked item under this root". Since that is syntactically identical to naming a specific item, the skill fetches the work type and tests, rather than assuming.

The central batching idea: **the release unit is the release unit.** Its items merge onto that unit's own integration branch, not your base branch; when its last item merges, one release pull request carries the whole batch through the complete review stack. Your base branch only ever receives whole, reviewed release units — or one-off items that settled every gate themselves.

::alert{type="note" title="It renders a progress table at every step transition"}
The loop's position is otherwise recoverable only from prose, so a compacted or resumed session would have to re-derive where it is. One row per numbered step, updated in place, with two rules that make it worth reading: it states **evidence, not intent** ("request registered in the timeline", never "requested" — the underlying GitHub mutation reports success while sometimes creating nothing), and **every configured engine gets its own row**, including an explicit "not configured" one, because a missing row is indistinguishable from a forgotten engine. On the fast path the cloud rows say *deferred* rather than going missing, for the same reason.
::

### Working base: the release unit's integration branch by default

Derived automatically from the selected item — no prompt. Precedence:

1. **Explicit override** — a branch passed in the arguments, or a non-null `integrationBranch` in config (the manual, cross-cutting initiative branch) — wins outright.
2. **A release-unit ancestor is found** (the default path) — the working base is that unit's **integration branch**, named per your configured pattern, e.g. `jane/03-14-26/I20104-attachment-storage`. The loop *reuses* an existing branch for that unit — from [handoff memory](/developer-experience/agentic-skills/claude-code-skills-overview#what-project-memory-means-here), or by looking up a remote `*/<number>-*` branch — and creates one off a fresh base branch only on the unit's first item. The date in the name is the branch's **creation** date, never re-minted. It announces which branch it reused or created, because the derivation is otherwise silent and the next session needs to know where the unit is accumulating.
3. **No release-unit ancestor** — a one-off, or a plan whose leaves sit directly under a higher container — falls back to your base branch: the classic flow, with the full per-item pull-request ritual.

The ancestor is resolved by walking the parent chain and **fetching each ancestor's work type explicitly**. That sounds like a detail and isn't: the hierarchy endpoint returns only numbers and titles, so matching a work type against it silently finds nothing, falls through to the base branch, and ships an item straight to production-bound code outside its release unit. And if no ancestor matches a **configured** release-unit type, the loop first checks that the configured type still exists in your hierarchy — a renamed type or a config typo has to stop and ask, never silently conclude "no release unit".

### Fast develop mode — stories on an integration branch have no pull request of their own

Because the release unit is the release, an individual item on an integration branch **is not a release**, and the loop stops treating it like one. Such an item runs in **fast develop mode**: build → the local review engines → green local suites → a local `--no-ff` merge onto the integration branch. **No pull request is opened for it at all** — no draft, no cloud reviewer request, no CI run, no threads to reply to and resolve.

Nothing is dropped from the review stack; the *cloud half* is **deferred** to the release pull request, which is the only thing that reaches your base branch:

| | item on an integration branch (fast mode) | the release pull request |
|---|---|---|
| Claude adversarial pass | ✅ per item, at max effort | ✅ over the whole batch |
| Local review CLI | ✅ per item, locally | ✅ over the whole batch |
| Cloud reviewers | deferred | ✅ |
| CI | deferred | ✅ once, on the final reviewed diff |
| Full local suites | ✅ **required green before the merge** | ✅ |

The saving per item is a pull-request open, a cloud-reviewer request and poll, a CI run, and the thread bookkeeping — all of it ceremony on work that was never going to reach your base branch on its own. Every engine that actually reads the code still runs, at full effort.

::alert{type="warning" title="Three guards make this safe — and all three are mechanical, not judgement calls"}
**1. The mode is chosen by the resolved working base, nothing else.** Integration branch → fast mode. Base branch → the full per-item ritual, always. That means **every one-off keeps its own pull request**: no release follows a one-off, so its pull request is the only place cloud reviewers and CI will ever see that code.

**2. The release review is a FULL-DIFF review.** Under fast mode that pull request is the *first* time any cloud reviewer or CI has seen **any** of the release unit's code. The narrower scope that would otherwise apply — "each item was already reviewed at its own pull request, so just review the integration surface" — is false here, and following it would let a whole release unit ship having never been cloud-reviewed. That is the one way this mode could cost quality, and it is prevented here and nowhere else.

**3. There is a floor of at least one local engine.** If the resolved roster has no local review CLI *and* no build-time adversarial pass covered the item, the loop routes it through the full pull-request ritual instead and says why. A fast-merged item with zero engines behind it is the one outcome this mode has to make impossible.
::

Two smaller consequences. The **local suites are the item's only mechanical gate** — with no CI behind it, type-checks and the full test suite must be green before the merge, and the pass counts go in the commit body as the durable evidence that the gate ran. A red suite is a stop, never "the release will catch it": at the release it arrives with N items of diff to bisect. And the whole mode is controlled by `epicIntegrationBranches.fastStoryMerges` in your config — turning it off returns every item to its own pull request.

::alert{type="danger" title="That gate only exists if you configured a test command"}
"The local suites are the only mechanical gate" has a precondition that is easy to miss: fast mode is **on by default**, so a repo that never set `verify.test` gets items merging onto an integration branch with **nothing mechanically verifying them at all**. They are still reviewed — the local engines are not optional — but nothing runs a suite, and the first thing that does is the release pull request, with the whole batch to bisect.

Either configure `verify.test`, or set `epicIntegrationBranches.fastStoryMerges.enabled: false` so every item goes back to its own pull request and CI. See the [configuration reference](/developer-experience/agentic-skills/configuration-reference#verification).
::

### The steps, in order

These numbers are the skill's own, not a retelling — `build-item`'s progress table renders one row per step and labels it exactly this way, so "step 4a" or "step 6.5" in a running session means the step of that name below. Note that the sequence runs 0–8 with a **6.5**, and there is no step 9.

- **0. Select the item and derive its working base.** Resolve a plan root (from the arguments or prior handoff memory) — if neither yields one unambiguous root and several plans are open, it stops and asks, because a wrong root silently executes the wrong plan. Then pick the highest-priority, not-Done, unblocked leaf in the earliest-dated open container on the critical path — the same canonical next-unblocked definition the planning skills use. It re-fetches the item's **full** description and validates it against the actual codebase before treating anything in it as true, checks whether the work is gated on something only you can do, and reports the whole **ready-set** of unblocked candidates, not just the pick, so parallel waves stay visible even though execution is serial. Zero candidates is a clean exit with the terminal state named — plan complete, blocked, or gated — never a loop back to re-ask.
- **1. Mark In Progress** — a real status move on the live item, confirmed before branching.
- **2. Branch** — invokes `branch-feature`, passing the working base explicitly.
- **3. Build** — invokes `ultracode-build`, which owns the understand/build/adversarial-review engine and hands back three lists: deferrals, deviations, and untracked deferrals.
- **4. Review** — and *which path runs is decided by the working base from step 0*, never by the diff or how the run feels:
   - **4a — fast mode** (integration branch): no pull request. The adversarial pass already ran at step 3; `review` is invoked in its **local-only mode** against the integration branch and returns triaged findings. Every confirmed finding is fixed and committed, and the full local suites must be green.
   - **4b — the full ritual** (base branch — every one-off, plus any item when fast mode is off): invokes `pr`, which opens the draft pull request and runs the review-and-settle engine.
- **5. Merge.** On the **fast path** there is nothing to merge on GitHub: pull the integration branch, merge the item branch with `--no-ff` so it stays a legible unit in first-parent history (the release body and the remaining-work counts are read off those merges), push, and only **after that push succeeds** delete the item branch locally and remotely — if the push were rejected, deleting the remote branch would destroy the only remote copy of the work. If the integration branch moved while you were building, the refreshed branch is merged *into* the item branch first and the suites re-run. On the **pull-request path**, the rebase already happened before the ready-flip, so it doesn't happen twice; it checks whether the base moved, confirms the applicable checks actually **ran** at the current head (a `skipping` check is not a passing one), re-checks that zero review threads are unresolved — a late comment in the gap between settle and merge would otherwise merge silently unaddressed — and merges.
- **6. Completion ritual** — move the item to Done, set its dates to the branch-to-merge window, and confirm the pull-request link. A fast-mode item **has no pull request to link**, so it gets its merge commit SHA and integration branch recorded instead, with the release pull request linked later — the loop will not invent a number for it. If the build materially diverged from the written spec, it preserves the original description as a comment and rewrites the description to the as-built one, with the deviations listed and rationalized.
- **6.5. Capture untracked findings** — any real, out-of-scope finding with no existing home is spliced into the dependency graph via `insert-defect` or `insert-story` so a future iteration actually reaches it. A finding that belongs to an existing downstream item goes on that item instead. See [the planning loop](/developer-experience/agentic-skills/claude-skills-planning-loop).
- **7. Sync and proceed** — check out the working base, pull, assert a clean tree (the next branch creation aborts on a dirty one, so stray files would silently wedge the loop), persist the plan root and the integration branch to handoff memory, and emit a close-out counting the release unit's remaining items. That count is taken over **the release-unit ancestor step 0 resolved**, not the item's direct parent: for a nested item those differ, and counting the parent can reach zero while the unit still has open work — which would publish a partially complete release.
- **8. RELEASE the unit** — runs when step 7 finds the release unit at zero remaining items **and `autoRelease` is enabled**. With it off the loop reports the unit release-ready and stops, deliberately: a flag the loop ignored would be worse than no flag. It refreshes the integration branch from your base branch (**merge, never rebase** — shared item SHAs must not be rewritten), verifies locally, cuts the release pull request via `pr`, runs the **full** review stack over it, merges once green and settled, deletes the branch if configured to, comments the release on the release-unit item, links the release pull request onto every constituent item that deferred it, and syncs. Promotion to production stays a separate, owner-cut act — see the `release` section below.

### Two ways in: the plan walk and the one-off

`build-item` runs in one of two modes and **auto-detects which**, with no flag:

- **Plan-loop mode** — the item is part of a sequenced plan: it carries an execution-order `[N]` prefix or is wired into the dependency graph. The full loop applies: select next-unblocked, walk the chain, splice discoveries back in, loop.
- **One-off / single-shot mode** — the item is standalone, with **no `[N]` prefix and no dependency edges** (for example one just created by `create-story` or `create-defect`). Steps 1–6 run **verbatim** — the whole point is that the inner build loop is identical — but there is no plan root, no ready-set, no next-item selection, no numbering and no chain splice. It ships once and terminates, and its discoveries become their own one-off items.

::alert{type="warning" title="Two classification traps, both silent"}
The detection reads the item's **`relationships`**, which the default projection omits — so an item whose only plan signal is a dependency edge would look like a one-off and ship straight to your base branch, bypassing its integration branch. The skill requests the field explicitly for exactly this reason.

And a one-off's working base is your base branch **unconditionally**, not "because it has no release-unit ancestor". `create-story` and `create-defect` both offer a release unit as a parent, so a one-off filed under one genuinely does have that ancestor; without an explicit bypass the general rule would route it onto that unit's integration branch and strand it there until an unrelated release cut.
::

### Autonomy boundary

The loop runs select-through-next-item **without pausing between steps**. It stops and asks only at a genuine fork: work gated on a human or infrastructure decision that is yours to make; an ambiguous, risky or unverifiable review finding; or a destructive or outward-facing action. Everything else proceeds on its own judgment, with every deferral recorded explicitly — in the build plan, the pull request body, and project memory — rather than silently dropped. That is exactly the contract `/loop` needs to drive it unattended.

::alert{type="warning" title="Serial by design — do not fan out concurrently"}
It executes one item at a time on purpose. Branch creation aborts on a dirty tree, the build runs checks against one working tree and one local database, and the MCP writes to production — so concurrent branches would race on shared local and live state. The ready-set surfaced at step 0 shows where a plan's parallel waves *could* run; fanning them out is a human decision, not something the loop does itself.
::

## Branch creation: `branch-feature` and `branch-hotfix`

| | `branch-feature` | `branch-hotfix` |
|---|---|---|
| Branches off | the resolved working base, freshly pulled | a **fresh copy of the production branch** |
| Naming | `<prefix>/<MM-DD-YY>/<name>` | `<prefix>/hotfix/<MM-DD-YY>/<name>` |
| Called by `build-item`? | Yes — step 2 | No — standalone only |
| Pull request | opened later by `pr`, targeting the working base | opened later by `pr`, targeting the production branch |
| Use when | building a normal item through the loop | an urgent fix that must not carry unreleased work |

`branch-feature` is the everyday utility: abort on a dirty tree, sync the base, create, push with `-u`. If the working base is an integration branch that doesn't exist on the remote, it **stops** and says to create it first rather than silently falling back — a silent fallback would put the item on your production-bound branch.

`branch-hotfix` is heavier and standalone. It aborts on a dirty tree and recommends stopping your dev server before the switch, because it cannot do that for you. If your repository has a database reset or migration procedure that belongs with a production-based branch, it tells you to run it — and says plainly that the procedure is repo-specific and lives with the repo, asking rather than guessing if it doesn't know yours. It opens no pull request, because a fresh branch has nothing to compare. On a failure partway through it reports which step broke **and which branch your checkout is now on**, since the early steps leave you on the production branch and that is easy to miss.

## `ultracode-build` — the build engine

```
/devstride:ultracode-build I#### <one-line goal/scope>
```

The engine `build-item` invokes once a branch exists and the item is In Progress. It is not a selection tool and it neither opens a pull request nor merges — it hands back to the orchestrator. Three phases:

1. **UNDERSTAND** — build an evidence-backed picture of "done" before writing code, **provisioning readers proportional to the work rather than reflexively fanning out**. Three core lenses carry most builds: the *downstream contract* the new code must satisfy, the *module structure* it belongs in, and the *test plan* it must not break. Others are added only when warranted. A genuinely trivial change skips the fan-out entirely and is read inline — but "unsure" counts as substantive, because an unnecessary parallel pass costs little next to a missed contract mismatch. Output: a concrete build plan, and a buildable-now-vs-deferred scope line that becomes the pull request's deferred note. If understanding reveals the work is gated on something you must provision, it stops rather than building a half-thing around a missing dependency.
2. **BUILD** — small increment → checks green → commit, repeated. It reads and obeys your `conventionsDoc` — that file is the authority on your typing rules, styling, error handling and module boundaries, and it explicitly does not substitute conventions remembered from elsewhere. Commits are frequent and conventional. Type-checks and the touched tests must stay green; a red check is stop-and-fix, never commit-anyway. Generated artifacts are regenerated with your configured command and committed **separately** from hand-written code, and generated-file type errors are tolerated only where your config names them — fixed by regenerating, never by hand-editing.
3. **ADVERSARIAL REVIEW** — a parallel pass over the **hand-written diff only** (generated files excluded, computed against the working base), **mandatory at maximum effort on every item, with no trivial-diff skip**. What scales with risk is *breadth*: a one-liner gets one or two finder lenses with batched verification; a contained change two or three; anything crossing module contracts, deployed handlers, migrations or permission surface gets all five — correctness, security, contract-match, tests/false-green, cleanup/conventions — with per-finding verification. Stage two classifies each finding as **CONFIRMED**, **PLAUSIBLE** or **REFUTED**. Only the first two are fixed or explicitly deferred; **REFUTED findings are dropped, never "fixed"** — the verification stage exists precisely so finder suggestions are not blind-applied.

It hands back the item number, a one-line summary, green-checks confirmation, the scope line, an **untracked-deferral list** (empty is fine and normal, but it says so explicitly rather than omitting it), and a **deviations list** — every material divergence from the written spec, which feeds both the pull request body and the item's as-built reconciliation.

::alert{type="info" title="The lessons store"}
If your repo configures a `lessonsDoc`, the build engine reads it here as **advisory hypotheses, not rules** — machine-distilled from past review findings, never independently reviewed, so possibly stale or overgeneralized. A lesson that plainly applies to this code is the cheapest place to handle a known mistake class; one that doesn't is ignored silently. It never overrides your conventions doc, the item's spec, or a direct reading of the code. Only `review` writes to it. An absent or empty file is a completely valid state everywhere.
::

## Review first, CI last — and CI is held mechanically

The single most important property of the review stack is its **ordering**: every review engine settles *before* any CI runs, and CI then runs **once**, against the final reviewed diff.

This is enforced by machinery, not discipline — **in a repo configured for it**. When `review.openPullRequestsAsDraft` is on (the shipped default), `pr` opens every pull request as a **draft**, and every job in your workflows is gated on the draft condition, so while the reviewers work **no runner starts at all** — nothing to poll, nothing to triage. Marking the pull request ready, inside `review`, is the deliberate act that releases CI.

Turn that flag off and you have described a different repo, not a broken one: pull requests open non-draft, there is no ready-flip, and CI settles concurrently with review. The skills adopt that shape and say so. The half-configured case is the one to avoid — the flag on but your workflow jobs *not* gated on the draft condition, which silently gives you neither ordering. That gate is a setup step in your own repository; see [Getting the skills](/developer-experience/agentic-skills/getting-the-skills#_5-gate-your-ci-on-the-draft-condition).

The problem this solves: CI used to fire the moment a pull request opened, reviewers would then find things, fixes were pushed, and CI started over — the first run thrown away. The slow, serialized half of the pipeline was paid for twice and read twice.

Fast develop mode extends the same idea one level up. The engine set never changes; only its **granularity** moves. For an item on an integration branch the local engines run per item and the cloud half runs once for the whole unit at the release. For a base-branch item or a one-off, both halves run on that item's own pull request. Either way every line passes every configured engine before it reaches your base branch.

Two consequences worth knowing:

- **A draft pull request has no CI results, and that is not the same as green.** The skills assert a pull request is non-draft before merging.
- **A rebase after review has settled means the diff is no longer the one that was reviewed.** `review` compares the patch before and after; if it changed, the local engines re-run — and the cloud reviewers are re-requested when the delta is substantive — before CI is released.

::alert{type="danger" title="Never flip a pull request ready in the same breath as a push"}
Workflow gates are evaluated per event. A push while the pull request is still a draft fires an event that correctly skips; if the ready-flip lands before that event registers, **there is no later event to re-evaluate and CI never runs at all**. The failure reads as success: every job reports `skipping`, which is indistinguishable from a suite being legitimately non-applicable. `review` therefore lets the push register first, then *asserts* the flip took — by a cheap, path-filter-free gate job you can name in config, or otherwise by the appearance of a new workflow run — and close-and-reopens the pull request if it produced nothing. A skipped board read as a green one is a merge with no CI behind it.
::

## The review stack: `pr` → `review`

Two skills, each usable standalone. An item on an integration branch under fast develop mode never reaches **`pr`** — there is no pull request to open — but it does reach `review`, mandatorily, in the **local-only mode** described below: same skill, same triage, no cloud half and no CI. `pr` next runs for that release unit at its release.

### `pr` — creation, linking, and the pre-ship hold

```
/devstride:pr [item-number]
```

It authors the body rather than using `--fill`, rendering the sections from your configured template in order — the list is ordered and **closed**, so a caller's flavour (release-unit release, hotfix, production release) changes how sections are *filled*, never the section set. The shipped default is four sections: a plain-language description, a technical one, notable changes to architecture or behaviour, and testing steps. No AI-attribution text goes in a body.

It opens the pull request **as a draft** when your repo holds CI on drafts, and **requests every configured cloud reviewer in the same call** — that overlap is the single biggest wall-clock saving in the loop, so it is never deferred to a later turn. It iterates the configured reviewer list rather than assuming one bot: requesting only the first would leave the others never asked while the poll still waited them out. An empty reviewer list is legal and means nothing is requested.

It detects two shapes that are not its own flow: a **production release** (base and head match your release configuration) is handed to `release`; and an **epic release pull request**, whose body leads with the release unit and lists its constituent items, and which is merged without deleting the branch — the caller owns that cleanup.

**The pre-ship hold.** Some suites deliberately run locally at the ship boundary rather than in CI — your repo declares them as `preShipChecks`. When at least one of them both selects and matches this pull request, `pr` **declares a hold in the same invocation that starts the review**: settle the review, but stop short of releasing CI. Then it runs those suites against the final, base-refreshed diff, and only then re-invokes `review` in its named resume mode to flip and settle. The order is the entire point — let the flip happen first and a red pre-ship check forces a fix onto an already-reviewed, already-tested pull request, and that fix reaches CI having passed no reviewer. A declared hold that is never discharged strands the pull request as a permanent draft, so the skill must either finish or say plainly that it could not. With no `preShipChecks` configured, all of this is an explicit no-op.

### `review` — the review and CI-gating engine

```
/devstride:review [PR#]
```

It begins by **resolving the roster from config plus live probes, and announcing it**. The built-in adversarial pass is intrinsic and always present. A local review CLI is on the roster only if `review.localCommand` is set *and* its binary actually resolves. Cloud reviewers are exactly your configured list. With no config file at all the roster is the built-in pass alone — and that is a *configuration*, not a failure.

::alert{type="warning" title="Configured-but-failing is not the same as not-configured"}
A configured engine whose probe fails, or a configured cloud reviewer that never registers or never answers, is a **degradation of this run** and is reported as one. If that drops a production-bound pull request to a single engine, the loop **stops for a human review before releasing CI** — even in autonomous mode. An unconfigured engine, by contrast, is silent by design: the roster is simply narrower, and the loop says so and proceeds. Getting these two confused is how a gate disappears without anyone noticing.
::

The loop, once the roster is resolved. These are `review`'s own step numbers, worth getting right because other skills call the steps by name: note the **6.5** sitting between 6 and 7, and that the ready-flip — the act that releases CI — is **step 7**, which is what every other page means when it cites it. (A closing step 8 re-checks the threads and reports.)

- **1. Launch every stream concurrently** — the adversarial pass (skipped only when the build engine already covered this exact diff), the local CLI in the worktree (launched in the background with a long timeout, because a foreground kill mid-review looks *identical* to a clean review), and every configured cloud reviewer. A cloud request is confirmed by a **new timeline event**, not by the request call returning: the underlying mutation reports success even when it creates nothing.
- **2. Wait for the cloud reviewers** — one self-terminating background poll, bounded by your configured timeout, watching **reviewers only**: nothing is running on a draft, so there is nothing to interpret. Local findings are triaged while the poll runs. On timeout it proceeds with what it has and **records which reviewer never answered** — a pull request reported as fully settled while a configured engine silently stayed quiet is exactly the degradation this gate exists to prevent.
- **3. Collect both halves, scoped to this cycle** — inline threads **and** the review body, which carries findings with no thread including a collapsed low-confidence block that is treated like any other finding. Zero inline comments never means zero findings. It never filters by author login (one reviewer can report three different logins across three APIs, and a login filter returns zero rows indistinguishable from "nothing found"). Findings de-duplicate on **the claim, not the location** — two engines flagging the same line are only duplicates when making the same point — and a genuine duplicate keeps the *cloud* entry, since that is the one carrying a thread to answer.
- **4. Verify and triage** — read the actual code before changing anything, then sort each finding into exactly one bucket: refuted (dismissed with a posted rationale, never silently ignored), confirmed or plausible and in scope (fixed now), real but out of scope (captured onto the untracked-deferral list, because a finding left as pull-request prose is invisible to the loop forever), or genuinely ambiguous — the one bucket that legitimately stops an autonomous run.
- **5. Apply fixes and push** via `push`. It never opens a second pull request to land review fixes.
- **6. Reply to AND resolve every addressed thread.** "Addressed" means any terminal disposition — fixed, dismissed, or captured — and each gets **both** halves. Replying without resolving is the common half-done state: the finding was handled, but the pull request still shows open threads and reads as unreviewed. It resolves only threads it actually addressed, never a blanket clear, and it knows that an **"outdated" badge is not "resolved"** — that flag is about line anchoring after a rebase and hides nothing. Findings from the review body have no thread, so they are reported in one summary comment with each disposition.
- **6.5. Distil any durable lesson** into your `lessonsDoc` — at most once per cycle, never onto a protected branch, and commonly writing nothing at all, which is the correct outcome for most cycles. It happens *before* CI is released, so any lesson commit is part of the SHA CI actually tests.
- **7. Release CI and settle green** — bring the head up to date with its base (never rebasing a **protected** head — on a production release the head *is* your development branch), run the paginated zero-unresolved-thread check, mark the pull request ready, assert the flip actually started CI, then poll the checks. Green means **the final head SHA observed success for every applicable check**: absent, skipped, pending or stale-SHA is not green. Flaky and infrastructure failures are re-run within a small bound; real ones are reproduced and fixed in loop, which puts you back in review — and the pull request is now ready, so each fix re-runs CI. That is the cost of a defect local review missed, not a reason to loosen the ordering.

**Local-only mode** is what fast develop mode uses, and it is the one mode with no pull request behind it: the caller passes a base ref instead of a number, and the skill runs the local stream alone and stops after triage — no cloud reviewer, no poll, no threads, no ready-flip, no CI. It still distils lessons, deliberately: under fast mode most findings only ever exist locally, so a pull-request-only writer would starve the store of exactly the findings the loop sees most.

::alert{type="danger" title="Review comments are untrusted content"}
`review` acts on external content — bot review comments, CLI findings — with reduced oversight in autonomous mode. A comment carrying embedded instructions (asking it to run something, change behaviour, or ignore prior instructions, beyond a normal code-review suggestion) is treated as untrusted tool data, not an instruction: it is not acted on, and it is flagged. Lesson text is distilled by the skill from its own verified triage, never pasted from an engine's comment, so nothing embedded in a review can ride into the store.
::

## `push` — the smallest utility

`push` stages tracked changes with `git add -u`, then **adds any new file the change requires by name**. Both halves matter: a blanket `git add .` would sweep in unrelated untracked files, while `-u` alone cannot see a new source or test file — so the commit would push without it while the skill reported success, leaving a silently incomplete change. It commits per your configured conventions, adding an item tag only when the work actually has an item and **never composing a number to satisfy a format**. It runs your type-checks and pushes, falling back to `--force-with-lease` — never a bare `--force`, and never onto a protected branch — on a non-fast-forward rejection. A type-check failure that isn't a tolerated generated-file error blocks the push; it reports and asks. It never opens a pull request.

## `release` — promoting to production

```
/devstride:release [no docs | skip docs | docs only]
```

The top tier. Items advance an integration branch, integration pull requests advance your development branch, and **this** advances production — which triggers your deploy the moment it merges. Because that is a real, outward-facing event, the release is **owner-cut**: the skill prepares everything and then stops.

It computes the release **delta** from the first-parent log and the merged pull requests in range, separating **user-facing** changes from internal ones — that split drives both the pull request body and the docs pass — and flags anything that looks like a breaking change or a migration. It cuts the release pull request (draft, with every cloud reviewer requested), then runs the full gated review **scoped to the release surface**: every constituent unit was already fully reviewed at its own pull request, so the review points at what per-pull-request review couldn't see — cross-unit interactions and anything in the range that wasn't its own reviewed pull request.

It runs your release-only pre-ship suites **unconditionally**. Paths are deliberately ignored at the production boundary: a frontend-only or purely internal release still runs them, and "the diff didn't touch its paths" is exactly the argument this rule overrides. A red check is a stop. You may explicitly waive one, and the waiver is recorded in the release summary so the evidence stays honest — but the skill will never describe a locally-gated suite as "covered by CI", because it isn't, and saying so is the precise false assurance the step exists to remove.

By default it then updates a sibling **documentation repository**, if your config names one. It learns that repo's structure from the repo itself rather than hardcoding it — including checking how the site builds page routes before writing any internal link, since a shortened form that works for an existing page via a legacy redirect will 404 for a new one. It updates what the user-facing delta made stale and writes a new release note when the delta is large and user-facing. Pass `no docs` — or `skip docs`, which the skill accepts identically — to suppress the phase entirely, or `docs only` to run it against an already-shipped release.

Finally it presents the release for go-ahead: the pull request state, the review tally, the delta, **each pre-ship check by name with its result or waiver**, the docs outcome, and a reminder of what merging triggers — quoted from your own config rather than assumed. Then it asks. Invoking the skill is intent to *prepare* a release, never standing authorization to deploy one.

## How it composes

```
/devstride:build-item <item|next>
├─ 0. select item + derive working base
│     (full projection incl. relationships; ready-set;
│      release-unit ancestor → its integration branch
│      [reuse existing, else create off the base branch] · none → base branch)
├─ 1. mark In Progress                    (live item write)
├─ 2. branch-feature I<####>-<slug>       (off the working base)
├─ 3. ultracode-build I<####> <scope>
│     ├─ UNDERSTAND  (readers proportional to the work → build plan)
│     ├─ BUILD       (commit often, keep checks green, obey conventionsDoc)
│     └─ ADVERSARIAL REVIEW (mandatory, max effort, breadth scales with risk;
│                            finders → verify → fix CONFIRMED/PLAUSIBLE,
│                            drop REFUTED)
│           └─ hands back: scope line · deviations · untracked deferrals
├─ 4a. FAST MODE — working base is an INTEGRATION BRANCH
│     │  (no PR, no draft, no cloud reviewer, no CI — deferred to step 8)
│     ├─ adversarial pass: already ran at step 3
│     ├─ review LOCAL-ONLY   (local CLI vs the integration branch)
│     ├─ fix every confirmed finding
│     └─ full local suites MUST be green   (the only mechanical gate;
│                                           pass counts recorded in the commit)
│
├─ 4b. FULL RITUAL — working base is the BASE BRANCH (one-offs; fast mode off)
│  └─ pr   (driven mode; base = working base)
│     ├─ open PR as a DRAFT + request every cloud reviewer in the SAME call
│     ├─ declare a PRE-SHIP HOLD if any local suite matches this diff
│     └─ review   (the review + CI-gating engine)
│           ├─ resolve + ANNOUNCE the roster
│           ├─ launch all streams concurrently
│           ├─ poll REVIEWERS ONLY (nothing runs on a draft)
│           ├─ collect BOTH halves: inline threads + review body
│           ├─ verify + triage: dismiss REFUTED / capture out-of-scope / ask
│           ├─ push  (commit + typecheck + push the fixes)
│           ├─ reply AND resolve every addressed thread → 0 unresolved
│           ├─ distil lessons (before CI, so the tested SHA includes them)
│           └─ rebase → gh pr ready ← RELEASES CI → assert it started → green
│     └─ (held? run pre-ship suites, then resume review to flip and settle)
├─ 5a. fast merge  (from 4a — merge --no-ff onto the integration branch, push,
│                   THEN delete the item branch local + remote)
├─ 5b. PR merge    (from 4b — base moved? checks RAN? zero unresolved? merge)
├─ 6. completion ritual  (Done, dates, PR link — or the merge SHA + integration
│                         branch when 4a left no PR — as-built reconciliation)
├─ 6.5. capture untracked findings → insert-story · insert-defect
├─ 7. sync + close-out (count remaining leaves under the RELEASE-UNIT ancestor)
└─ 8. RELEASE THE UNIT   (auto only when autoRelease is on)
      refresh from the base branch (merge, never rebase) → verify locally →
      pr in release-unit mode → FULL-DIFF review (first cloud pass over any of
      this code under fast mode) → merge → delete branch (if configured) →
      comment + link the release PR onto every item → sync
      ── promotion to production stays owner-cut: /devstride:release
```

`branch-hotfix` is deliberately absent from the diagram — it is a standalone entry point for emergencies, not a step the loop calls.

The **one-off** path (`create-story` / `create-defect`) runs the same steps once and terminates instead of looping. Step 0 is *reduced*, not skipped: the item is already chosen, so plan-root resolution, the ready-set and next-item selection all drop out — but the gating check (is this work blocked on something only you can provision?) and the validation of the item's spec against the actual codebase still run, and step 0 is also where the working base is pinned to your base branch. Steps 1–6 then run **verbatim** — the whole point being that the inner build loop is identical to a planned item's. At step 6.5 follow-ups become their own one-off items rather than a splice into a plan that doesn't exist, and step 7 syncs, emits a close-out for the single item and stops. Step 8 never applies: a one-off is its own release.

## Repo configuration

Every concrete value on this page — the base and production branches, the type-check and test commands, the local review CLI, the cloud reviewers, the draft/ready mechanics, the pre-ship suites, the release and docs settings — is **not hard-coded inside the skills**. It lives in one file in your repository, `.claude/ds-config.json`, which the delivery skills load and treat as authoritative. If the file disagrees with a literal printed in a skill, the file wins; if it is absent, the skills fall back to their inline defaults and say so.

The planning skills barely touch it — four read nothing from it at all, and `plan` reads two optional keys. So adopting the delivery loop in a new repository is **writing a config file**, not editing skills — with a light skill edit needed only where a repository's structure genuinely differs from anything the defaults anticipate. Every key is documented in the [configuration reference](/developer-experience/agentic-skills/configuration-reference).
