# Guided Setup

You do not have to write `.claude/ds-config.json` by hand. `/devstride:setup` reads your repository, works out most of the file from what it finds, asks about the rest, writes it, and then **runs it** to check it was right.

The last part is the one that matters. A config file is easy to get subtly wrong and hard to notice you have — a command name that drifted, a branch that was renamed, a review engine declared but not installed. None of those announce themselves. They surface later, from inside the delivery loop, as a failure several steps removed from its cause. Setup finishes by executing the config it just wrote, while you are still sitting there to fix anything it finds.

::alert{type="note" title="Run it once, then re-run it whenever the repository changes shape"}
Setup is not a one-time wizard. Re-running it on a configured repository re-detects everything, proposes only what actually changed, and **merges** — it never overwrites your hand edits, your annotations, or keys it does not recognize. Adding a workspace, renaming a branch, or installing a review engine are all good reasons to run it again.
::

## Before you start

Install the plugin and connect it to your organization first — that is [Getting the skills](/developer-experience/agentic-skills/getting-the-skills), and this page assumes you have done it.

One thing genuinely matters before you run setup: **be signed in to DevStride**. Setup maps your organization's real work types onto the loop's roles, and it can only do that against a live connection. Without one it will tell you plainly, offer to carry on without that part, and leave the rest of the config perfectly usable — but you will have to come back and finish it. Connecting first is less work.

```
/devstride:setup
```

## What it works out on its own

The design rule is **detect before you ask**, because every question is friction in your first ten minutes with a tool that has not done anything for you yet. Most of this file is already sitting in your repository:

| It looks at | To work out |
|---|---|
| Your lockfile, or `package.json`'s `packageManager` | Which package manager your commands should use |
| `package.json` scripts, per workspace in a monorepo | Your typecheck, test and lint commands |
| Your workspace globs | Whether commands need a `cd <workspace>` prefix |
| `.github/workflows/` | Your CI provider, and whether its draft gating actually works |
| Your git branches | Which branch is the base, which is production, which hotfixes cut from |
| Your `PATH` and `gh` | Which review engines you actually have |
| `AGENTS.md` / `CLAUDE.md` / `CONTRIBUTING.md` | Your conventions doc — the file the build engine reads and obeys |
| An existing pull-request template | Your pull-request body sections |

Every value it reports comes with the evidence that produced it, and an honest label:

- **Detected** — one unambiguous answer. It becomes a default you confirm in bulk.
- **Ambiguous** — several plausible answers, or one worth confirming. It becomes a question with the candidates offered.
- **Unknown** — your repository does not answer this. It becomes a question with no prefill.

**Ambiguous is a feature, not a shortcoming.** A wrong value arrives wearing the authority of evidence and gets accepted without reading, so setup refuses to guess wherever guessing is the easy option: two different lockfiles is a question, not a pick; several workspaces with a `test` script is a question, because only one command can be *the* test command; and a cloud reviewer stays a candidate even when your GitHub authentication is fine, because authentication is a precondition and not proof that a review request will ever register.

## What it asks you

As little as it can. Everything it detected is confirmed in one pass rather than forty questions, and only the genuinely unresolved rows are asked individually.

Three things no inspection can reach, so they are asked every time:

1. **Which of your work types are which.** The loop reasons in two roles — the *release unit* whose completion cuts a release, and the *leaf* items it actually builds. Setup reads your organization's hierarchy, proposes the mapping from its structure, and asks you to confirm. It confirms even when the answer looks obvious, because this single choice decides where the loop branches, what it counts down to, and what "a release" means in your repository.
2. **What merging to your production branch actually does.** One plain sentence — whether it deploys, and through what. The release skill quotes it back to you at the production gate so you know exactly what you are approving.
3. **Whether you have a sibling docs repository** the release skill should update. If you do, it takes the whole thing at once — path, branch, whether pushing deploys — because a half-answered docs setting stops the release skill at its first read.

::alert{type="info" title="Your answer always wins"}
If you override something setup detected, the override is what gets written. Detection never quietly reapplies itself at write time.
::

## What it writes — and what it deliberately will not

One file: `.claude/ds-config.json`. That is the entire write boundary. Setup does not touch your application code, your `CLAUDE.md`, your permission settings, or your CI workflows — not even to fix something it has just told you is broken.

Two of the values it writes are decisions rather than detections, both set to the cautious side:

- **`autoRelease` is written `false`.** A completed release unit merging to your base branch without a human saying so is a thing to switch on after you have watched the loop run, not to inherit on day one.
- **Fast item merges are only enabled with a local engine and local suites behind them.** Under that mode an item gets no pull request and no CI of its own, so those local suites are the only gate it receives. With nothing local configured, setup turns the mode off and says why.

More generally: **setup will not write a config claiming an engine you do not have.** No local review CLI means the key is omitted and the built-in adversarial pass is your local gate — which is a legal configuration, not a degraded one. No cloud reviewer means an empty list, and nothing is ever requested or waited on. Every later run reads these keys as fact, so an aspirational roster does not fail loudly; it quietly changes what gets reviewed.

## The part that makes it trustworthy: it runs the config

Setup does not end at the write. It executes what it wrote:

1. **Your verify commands actually run** — typecheck and lint are invoked for real. Tests are *offered*, never forced, because a suite can run for half an hour; declining is recorded as skipped rather than folded into a pass.
2. **Your branches resolve**, and `protectedBranches` still contains your base and production branches — that list is what stops the loop force-pushing or deleting them.
3. **Declared review engines respond.** Only the ones you declared; an engine you never asked for is not a gap.
4. **Your work-type roles still resolve.** Types get renamed and archived, and the failure is silent — the loop simply matches nothing and treats every item as a one-off.
5. **The lessons store has somewhere to live** — the directory, not the file. The file appearing later is normal.
6. **Your CI ordering is self-consistent** — a warning only, and never a workflow edit.

Every check ends **pass**, **fail**, **skipped** or **unverifiable**, and every check runs even after one fails, so three problems are three lines in one report rather than three restarts. Your repository is called loop-ready only with zero failures; skips and unverifiables are fine as long as the verdict names them.

::alert{type="note" title="Two things the verdict tells you, so a failure is not misread"}
If your **working tree was dirty**, an uncommitted change is a far likelier cause of a failing typecheck than your config is. And if the run was **offline**, the connection and cloud-access checks come back *unverifiable* rather than failed — a laptop on a train is not a broken setup.
::

### When a check fails

Every failure is reported with what it means and the exact fix. The full table — symptom, likely cause, fix — ships with the plugin as the authority, at `skills/setup/references/validation-checklist.md`; the skill reads it as it runs, so what you are told matches what is shipped. The ones people hit first:

| What you see | Usually | Fix |
|---|---|---|
| A verify command exits non-zero on a clean tree | The script name drifted from `package.json` | Re-run setup to re-detect, or edit the entry |
| A branch ref does not resolve | The remote has not been fetched in this clone | `git fetch origin`, then validate again |
| A declared review CLI does not respond | Not installed, or it exists only as a shell alias | Install it so it is on `PATH`, or clear the key and let the built-in pass be your local gate |
| A work-type role no longer resolves | It was renamed or archived in your organization | Re-run setup and confirm the mapping against the current hierarchy |
| The organization check is unverifiable | You are not signed in — the symptom is *absent tools*, not an error | Run `/mcp`, connect, and validate again |

One honest caveat, stated in the checklist and worth repeating: a passing cloud-reviewer check means *nothing is obviously in the way*. Whether a review request actually registers is only ever settled on a real pull request, because the request reports success even when it creates nothing.

## Re-running it later

Run `/devstride:setup` again any time. It re-detects, compares against the file you already have, and proposes **only what would change** — including additions for keys written by hand or by an older version, and removals for things you tell it no longer apply, such as a docs repository that has gone away.

What survives a re-run, unconditionally:

- **Keys it does not recognize.** They may be newer than your installed version, or something you added deliberately.
- **Every `_`-prefixed annotation.** Real configs carry `_readme` notes explaining hard-won reasons next to the values they explain. A rewrite that drops them destroys the reasoning while leaving the file working.
- **Anything it did not propose changing.** Silence is not consent to revert.

Setup authors this file; it does not become a new layer of precedence over it. The existing contract is unchanged — the file wins over the plugin's shipped defaults, including over anything setup itself wrote.

## After setup

You have a validated config. Two things worth doing next:

- Run [`/devstride:doctor`](/developer-experience/agentic-skills/skill-audit) any time the loop behaves unexpectedly. It is read-only, it checks the whole setup rather than just the config, and it never changes anything.
- Start planning: `/devstride:plan <item>` — see [the planning loop](/developer-experience/agentic-skills/claude-skills-planning-loop).

And when you want to know what a key means or set one setup never asks about, the [configuration reference](/developer-experience/agentic-skills/configuration-reference) covers every key in the file.
