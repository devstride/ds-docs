# DevStride for Claude Code

Shipping a piece of tracked work is a sequence almost everyone knows and almost nobody has written down: figure out what to build next, move it to In Progress, branch correctly, build it, review it honestly, get it through CI, merge, update the item, sync, pick the next thing. It is well understood and never *encoded* — so two engineers do it two ways, and every lesson learned ("rebase before merging", "never merge red CI") lives only in that afternoon's chat transcript.

The **`devstride` plugin for Claude Code** is that loop, written down once. Seventeen skills cover both halves of it: shaping a roadmap in your DevStride organization, and then walking that roadmap one item at a time against **your own repository** — branch, build, adversarially review, merge, release.

It is a public plugin. You install it from a marketplace like any other, run one guided setup command to point it at your repo, and it runs against your organization and your codebase. DevStride's own engineering team installs it exactly the same way.

::alert{type="note" title="These pages describe plugin v0.7.0"}
Everything in this section — skill names, step numbers, config keys and defaults — was verified against **`devstride@devstride` v0.7.0**. Installed plugins do not update themselves, so two people can be running different revisions of the loop with nothing in the repository saying so. Run `claude plugin list` to see which version you have.
::

::alert{type="info" title="Container, release unit, leaf — and MCP"}
The skills reason in **roles**, not in any one organization's work-type names, and three of those roles appear on every page here:

- A **leaf** is an executable, roughly-one-day item — a Story or a Defect in a typical setup. It is the unit the delivery loop builds and ships.
- A **release unit** is the container whose completion cuts a release — usually an Epic. It is the level that gets its own branch and its own release pull request.
- Everything above that is a **container** — a Capability, a Solution, a Module, whatever your organization calls its upper tiers.

The roles are resolved from *your* hierarchy at runtime, so a shallower or deeper hierarchy simply has fewer or more container tiers. Wherever these pages say "Epic" or "Story", read the level in your organization that plays that part.

One more piece of vocabulary: **MCP** (Model Context Protocol) is the standard way a tool like Claude Code connects to an external system. The plugin bundles a DevStride MCP server, and that connection is how every skill reads and writes your roadmap. When a page says "the MCP writes to production", it means those roadmap writes.
::

## Two kinds of skill: the shared loop, and your own ops

The plugin deliberately carries **only what generalizes**. Everything a skill needs that is specific to a repository is externalized into that repository's `.claude/ds-config.json` — never baked into skill text.

That leaves a natural split, and it is the pattern the plugin exists to demonstrate:

- **The plugin** owns the shared delivery loop: planning, selection, branching, building, review, release. It works in any repository, against any DevStride organization, because everything variable is configuration.
- **Local skills in your own repo's `.claude/skills/`** own the things that *cannot* travel — a dataset builder that knows your fixture generator, a database reset that knows your dump layout, an internal document of the reasoning behind your own conventions. These are exactly the skills a plugin should not carry, because they would be meaningless (or dangerous) anywhere else.

DevStride's own monorepo runs precisely this way: it installs the plugin like any other customer and keeps a handful of repo-local skills for its own fixture and database tooling. If you find yourself wanting to edit plugin skill text to encode something about *your* repo, that is the signal — the value belongs in your config file, or in a local skill of your own.

## The default that surprises people: most items get no pull request

Out of the box, **individual items do not get a pull request of their own.** An item that sits under a release unit is built on that release unit's own long-lived integration branch, reviewed there by the local engines, verified against your local suites, and then merged **locally** onto that branch. Nothing is opened on GitHub for it.

What does get a pull request is the **completed release unit**. When its last item lands, one release pull request carries the whole batch — cloud reviewers, CI, the lot — and that is the only thing that reaches your base branch.

This is deliberate, and the reasoning is on [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop) page: no engine that actually reads the code is skipped, only the per-item *ceremony* around work that was never going to reach your base branch on its own. But it is genuinely surprising on a first run if you were expecting a pull request per item, so it is worth knowing before you start rather than after. Two exceptions keep their own full pull-request ritual: a one-off ticket or bug that is not part of any plan, and any item in a repo where the mode is turned off (`epicIntegrationBranches.enabled: false`).

## The safety model

Every skill that touches DevStride items shares one non-negotiable fact, stated at the top of each of those skill files: `build-item`, `plan`, `insert-story`, `insert-defect`, `create-story`, `create-defect`, `rationalize-gantt`, `release`, and — as a reads-are-safe caveat — `comprehend-plan`. `pr` touches the MCP too, but only to link a finished pull request to its item. The skills that never call DevStride at all (`branch-feature`, `branch-hotfix`, `push`, `ultracode-build`, `review`) simply don't mention it; they operate on git, your local checkout, and CI.

::alert{type="danger" title="The DevStride MCP targets PRODUCTION"}
The MCP server these skills call is `api.devstride.com` — your real, live workspace. There is no draft mode, no sandbox, no dry-run. When a skill calls `create_item`, `update_item`, `add_relationship` or `bulk_update_items`, that write lands on your organization's roadmap **immediately** and is visible to every real user of it. A status move, a new Epic, a rewritten description — none of it is a preview. Treat every write as a real, user-visible action.
::

Two consequences are baked into how the skills are written:

- **Planning skills get explicit sign-off before writing.** `plan` runs a whole interactive discovery loop and creates not one item until you have confirmed the full container → release-unit → leaf shape. `insert-story` and `insert-defect` are single-item writes, and `insert-defect` additionally asks before queue-jumping a bug ahead of already-planned work rather than silently reprioritizing your roadmap. `create-story` and `create-defect` confirm where the item lands — which parent, which board — before creating it.
- **Delivery skills treat item changes as real even though the code isn't live yet.** `build-item` moves an item to In Progress, and later to Done, as those transitions happen. Those are real changes to a live item regardless of whether the pull request has merged; the MCP cannot exercise branch code, so it has no way to "hold" a write until the code ships.

Code changes are different, and deliberately so. They go through ordinary git branches and pull requests, exactly as they would without any of this: a branch, a diff, review engines, CI, and a human-reviewable history stand between a change and your base branch. There is no equivalent safety net on the item side — which is exactly why the skills that touch items carry the heaviest confirm-first language.

::alert{type="warning" title="Some actions are destructive or hard to reverse, and get their own guard"}
- **`rationalize-gantt` overwrites a plan's stored dates across the whole tree** — including real completion dates a previous loop stamped on shipped items. It confirms the scope up front, and it refuses to run until DevStride's organization-wide dependency propagation (**Enable Link Mode**, in Settings → Organization) is off. There is no API to flip that setting, so the skill asks you to do it and then *verifies* with a probe write and read-back rather than trusting the answer. It also removes and repoints dependency edges — real graph surgery, one reviewed decision at a time.
- **`branch-hotfix` branches off a fresh copy of your production branch**, so an urgent fix is built against what is actually running rather than whatever is queued on develop. If your repo has a database reset or migration procedure that belongs with that, the skill tells you to run it — it does not guess what that procedure is.
- **The production release is owner-gated.** `release` prepares everything — the release PR, the full gated review, the docs pass — and then **stops** for an explicit go-ahead before the merge, because that merge is what triggers your deploy. Invoking the skill is intent to *prepare* a release, never standing authorization to deploy one.
::

Two smaller safety properties are worth knowing because they are easy to assume away. The skills treat **external content as untrusted data**: item descriptions, comment threads, and bot review comments regularly contain text, and a comment carrying embedded instructions is flagged, never obeyed. And **item numbers are looked up, never composed** — before writing an `I#####` into a commit message, a PR body or a code comment, the skill fetches it and confirms the title matches. A plausible-looking number is not a label; it is an address into live data, and a wrong one points at somebody else's work.

## The autonomy pattern: full-auto, except at genuine forks

Most of these skills — especially the delivery orchestrator, `build-item` — are written to run **end-to-end without pausing**. `build-item` is designed to be driven under `/loop`: select, mark In Progress, branch, build, review, merge, run the completion ritual, sync, next — with no confirmation prompt between steps.

::alert{type="info" title="`/loop` is Claude Code's, not the plugin's"}
`/loop <command>` is Claude Code's own repeat mechanism: it re-runs whatever command follows it, over and over, until you stop it. It is not part of this plugin and knows nothing about DevStride — `/loop /devstride:build-item` simply means "keep running `build-item`", which is what walks a whole plan instead of shipping one item. **To stop it, press `Esc`** to interrupt the current run, or just say "stop looping". Nothing here needs `/loop`; every skill runs perfectly well on its own, and running one item at a time is the right way to start.
::

That autonomy is bounded, not unlimited. Every orchestrating skill stops and asks at a genuine fork:

- **A human- or infrastructure-gated decision** — work blocked on DNS, cloud provisioning, a payment provider, a secret, an account only you can create.
- **An ambiguous, risky, or unverifiable finding** — a review finding the automation cannot confirm on its own, or a merge conflict it cannot resolve safely.
- **A destructive or outward-facing action** — anything in the guard list above, or any write it cannot cleanly undo.

Everything else proceeds on the loop's own judgment, with every deferral recorded explicitly — in the build plan, the pull request body, and project memory — rather than silently dropped.

### What project memory means here

Several skills "persist the plan root to project memory" or "read the integration branch from handoff memory". Both phrases mean the same thing: **Claude Code's own per-project memory**, the notes it keeps for the repository you are working in and reloads at the start of a session. It is not a DevStride feature and nothing about it is written to your roadmap.

It matters because it is what makes the loop *resumable*. When `plan` finishes, it writes down which item is the plan root; when `build-item` finishes an item, it writes down that root and the release unit's integration branch. So a bare `/devstride:build-item` in a fresh session picks up the right plan and the right branch instead of asking you again or guessing wrong. If that memory is empty — a new machine, a cleared session — the skills ask rather than assume, which is the correct failure and not an error.

::alert{type="note" title="plan is the deliberate exception"}
`plan` breaks this pattern on purpose, and says so in its own instructions: it is an **interactive, loop-based skill throughout**, not a one-shot generator. Planning — scope boundaries, sequencing trade-offs, what is V1 versus deferred, which items are hard gates versus parallel waves — needs real human judgment at every level of the hierarchy, not just at a final sign-off. It asks qualifying questions in rounds and gets explicit confirmation at each level before going deeper. If you try to skip that loop entirely, it pushes back once, then complies while labelling every unconfirmed decision as an explicit assumption. Once the shape is confirmed it does fan drafting out in parallel — but the judgment calls stay in the conversation with you, never inside that fan-out.
::

The contrast is the thing to remember: `build-item` is a loop that only stops at genuine forks; `plan` is a loop that keeps you in the room throughout, because the thing it produces — the shape of the roadmap itself — is exactly the decision this system will not make on your behalf.

## Which skill do I run first?

- **Building out a whole new hierarchy** — turning a container item into a real, dependency-wired plan through the interactive discovery loop — start with **[the planning loop](/developer-experience/agentic-skills/claude-skills-planning-loop)** and run `/devstride:plan <item>`.
- **Adding one Story or Defect to a plan that already exists** — don't reach for `plan`; run `/devstride:insert-story` or `/devstride:insert-defect` directly. `plan` is for building or extending a whole hierarchy.
- **Shipping something already planned** — picking up the next unblocked item and carrying it through branch, build, review and merge — start with **[the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop)** and run `/devstride:build-item` (under `/loop` to walk the whole plan).
- **Handling a one-off ticket or bug that isn't in any plan** — run `/devstride:create-story` or `/devstride:create-defect`. They create the item, place it, assign it to you, and deliver it through the same build loop **once** — single-shot, no plan walk.
- **Cutting a production release** — run `/devstride:release`. It prepares the release and stops for your go-ahead.

If you are unsure which situation you are in: if there is no item yet with an implementation-ready spec and dependency edges, you need the planning loop first. If the item already exists and just needs building, go straight to the delivery loop. If the work isn't tracked at all and isn't part of a sequenced plan, the one-off `create-*` skills create and ship it in one shot.
