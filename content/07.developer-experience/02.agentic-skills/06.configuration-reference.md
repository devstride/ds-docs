# Configuration Reference: `.claude/ds-config.json`

The `devstride` plugin ships no configuration for anybody's repository. Everything repo-specific — branch names, how to type-check and test, which review engines exist, what a release means — lives in **one file in *your* repository**: `.claude/ds-config.json`.

Three rules govern the whole file, and they are worth reading before the tables:

- **It lives in the consuming repo, not the plugin.** The skills load it from the repo root of whatever project they are running in. The plugin never carries a copy of anyone's config, and a config committed to your repo travels with your repo.
- **The file always wins.** Every skill states its concrete branches, commands, and paths inline as *shipped defaults, kept for readability*. Wherever the file disagrees with a literal printed inside a skill, the file is authoritative. Where the file is absent entirely, the skills fall back to the inline defaults and say so out loud rather than pretending they were configured.
- **Every key is optional.** An absent key is a documented state, not an error, and each entry below says what happens when it is missing. Several keys have a *legal empty value* that means "this repo has none of that" — `review.localCommand: null`, `review.automatedReviewers: []`, an empty `preShipChecks`. Those are configurations, not degradations, and the skills treat them as such.

::alert{type="note" title="Verified against plugin v0.5.0"}
Every key, default and behaviour on this page was checked against the skill text shipped in **`devstride@devstride` v0.5.0**. Installed versions drift between machines — an installed plugin stays where it is until someone updates it — so run `claude plugin list` and compare before assuming a key on this page exists in your copy. See [Getting the skills](/developer-experience/agentic-skills/getting-the-skills#_3-update).
::

**Reading the "Default" column.** It always means *the shipped behaviour when you omit the key*, and it takes one of three forms: a **concrete value** (`"develop"`, `true`) is what the skills substitute; **"resolved at runtime"** means there is no literal default at all — the skills work the answer out from your DevStride organization or your git identity each run; **"none"** means the key has no default because omitting it means the repo genuinely has none of that thing, and each row says what the skills then do instead. There is never a hidden default that differs from what this column says.

::alert{type="info" title="The delivery half reads this file; the planning half barely touches it"}
`comprehend-plan`, `insert-story`, `insert-defect` and `rationalize-gantt` read **nothing** from it — they resolve everything they need (work types, statuses, priorities) from your DevStride organization at runtime, which is why they are portable to any org with no setup.

`plan` is the exception, and it reads exactly two things, both optional, neither required for it to run:

- **`hierarchyRoles.releaseUnit`**, as a tie-breaker — when your hierarchy has several container levels and the release boundary is genuinely ambiguous, it consults the key so that the level it *plans* as a release is the same level the delivery loop *branches and releases* at. Without it (or without the file), it asks you instead.
- **`release.releaseSource`, `release.productionBranch` and `release.autoDeployOnMerge`**, to judge how fast your development branch reaches production — which is what makes "every release unit must be independently production-safe" a real constraint rather than a slogan, and drives the blast-radius questions it asks per release unit.
::

## A minimal starting config

Nothing below is mandatory, but this is a working shape for a repository that has a test suite, a type-check, and no review tooling beyond what the plugin brings:

```json
{
  "baseBranch": "develop",
  "protectedBranches": ["develop", "master"],
  "conventionsDoc": "AGENTS.md",

  "verify": {
    "typecheck": ["pnpm check:ts"],
    "test": "pnpm test",
    "testSingle": "pnpm test -- <path/to/test.spec.ts>",
    "lint": "pnpm lint"
  },

  "review": {
    "localCommand": null,
    "automatedReviewers": [],
    "openPullRequestsAsDraft": true
  }
}
```

That config gives you: correct branching, a build loop that keeps your own checks green, pull requests opened as drafts so CI runs once on the reviewed diff, and a review roster of one engine — Claude's own adversarial pass. Add a local review CLI and a cloud reviewer later and the roster widens without anything else changing.

It also leaves **`epicIntegrationBranches` at its defaults, which are on** — so most items will get no pull request of their own and will merge locally onto their release unit's integration branch, and only the completed release unit reaches your base branch as a pull request. That is the intended shape, but it is a surprising first run if you were expecting a PR per item. To watch every item go through its own pull request while you are learning the loop, add `"epicIntegrationBranches": { "enabled": false }` and take it out when you are ready.

::alert{type="note" title="Keys beginning with an underscore are prose, not data"}
Real-world configs are heavily commented using `_readme`-style sibling keys — `_integrationBranch_readme`, `_localCommand_mcp_readme`, and so on. JSON has no comments, so this is the convention that carries the *why* next to the value. They are documentation for whoever reads the file next (human or agent); no skill reads them as settings. Adopt the habit: the reason a glob exists or a flag is held off is exactly the thing that gets lost.
::

## Branches and working base

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `baseBranch` | string | `"develop"` | The branch feature work is cut from and merges back into. Wherever a skill step says "develop", it means this. |
| `hotfixBaseBranch` | string | `"master"` | The branch `branch-hotfix` cuts from, and the base a hotfix PR targets. |
| `protectedBranches` | string[] | `["develop", "master"]` | Branches that are never rebased, force-pushed, or deleted. Load-bearing in two places: `review` refuses to rebase a PR whose *head* is protected (a release PR's head is your development branch), and refuses to write the lessons store onto one. |
| `integrationBranch` | string \| null | `null` | **Explicit override.** Non-null pins one branch as the working base for *every* story regardless of its parent — the shape to use for a cross-cutting initiative that spans several release units. Set it back to `null` when the initiative finishes; left set, it silently routes all future work onto a branch that has already shipped. |
| `branchNaming.pattern` | string | `"<user-prefix>/<MM-DD-YY>/<branch-name>"` | The shape of a created branch name. The placeholder names are prose for a human reader, not a template language — `branch-feature` reads the pattern to learn the *shape*, then fills it from `prefixSource`, `dateFormat` and the name it was given. Repos commonly write the same shape as `"<prefix>/<MM-DD-YY>/<slug>"`; either spelling describes the same three parts. |
| `branchNaming.prefixSource` | string | resolved at runtime — git `user.name` first name, lowercased | How the `<user-prefix>` is derived; the skill asks rather than guessing when it is empty or ambiguous. |
| `branchNaming.dateFormat` | string | `"MM-DD-YY"` | The date component of a branch name. |

### `epicIntegrationBranches`

The default working-base mode: each **release unit** (in a DevStride org shaped Capability → Epic → Story, that is the Epic) gets its own integration branch, its stories batch onto it, and the completed unit reaches `baseBranch` as one fully-reviewed release PR.

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `epicIntegrationBranches.enabled` | boolean | on | Whether the loop derives a per-release-unit working base at all. `false` genuinely falls back — every story is built on `baseBranch` with its own pull request. |
| `epicIntegrationBranches.pattern` | string | `"<prefix>/<MM-DD-YY>/<epic-number>-<epic-title-slug>"` | The integration branch name. The date is the branch's **creation** date and is never re-minted; the loop looks for an existing `*/<epicNumber>-*` branch before creating one. |
| `epicIntegrationBranches.slugRule` | string | kebab-cased title, `[a-z0-9-]`, `[N]` prefix stripped, ~6 words | How the release unit's title becomes the slug in that branch name — casing, allowed characters, whether the execution-order prefix is stripped, how far to truncate. **It is read**, by `build-item` when it names a new integration branch, and its whole purpose is determinism: two sessions naming the same release unit must produce the same branch rather than each inventing a slug. |
| `epicIntegrationBranches.releaseTarget` | string | `"baseBranch"` | Where a completed release unit lands — the **base branch of the release pull request** `build-item` cuts when the unit's last item merges. The shipped default is your `baseBranch`; a repo that stages releases somewhere else (a `staging` or `next` branch) points this at that branch instead, and the release PR targets it without any other part of the loop changing. |
| `epicIntegrationBranches.autoRelease` | boolean | `false` (absent is read as off) | Whether the loop **cuts and merges** the release PR itself when the last story lands. With it off the loop stops at *release-ready* and waits for a human to release. A flag the loop ignored would be worse than no flag: the skill honours `false` literally. |
| `epicIntegrationBranches.deleteBranchAfterRelease` | boolean | `false` (absent is read as off) | Whether the integration branch is deleted after its release merges. A destructive remote cleanup, so `false` genuinely retains it. |

### `epicIntegrationBranches.fastStoryMerges`

Fast develop mode — the sub-block that decides whether an item on an integration branch gets a pull request of its own. See [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop) for what it actually does.

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `…fastStoryMerges.enabled` | boolean | on | When the working base is an integration branch, settle the story with the **local** engines and merge it locally — no PR, no cloud reviewer, no CI — deferring the cloud half to the release PR. Turning it off returns every story to its own pull request. |
| `…fastStoryMerges.requireLocalVerifyGreen` | boolean | `true` | The full local suites must be green before a fast-merged story lands. With no CI behind the story this is its only mechanical gate, which is why the loop records the pass counts in the commit body as durable evidence. |
| `…fastStoryMerges.epicReleaseIsFirstCloudPass` | boolean | `true` | Declares the consequence that must not be lost: under fast mode the release PR is the **first** time any cloud reviewer or CI has seen *any* of that code, so its review is a full-diff review of every story in the batch, not an integration-surface pass. |
| `…fastStoryMerges.localEngines` | string[] | none | Descriptive list of which local engines back a fast-merged story, for whoever reads the file. The roster the loop actually uses is resolved from `review.*` and live probes, not from this list. |

## Verification

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `verify.typecheck` | string[] | none | **An array of commands**, run before every commit and merge. Every entry runs, in order, and a failure in any one is a failure. This is the form `push` prefers and the form the build loop runs as it goes; a red check is stop-and-fix, never commit-anyway. |
| `verify.typecheckCombined` | string | none | The same checks expressed as **one** shell command. It is a *fallback*, not the primary: `push` runs the `verify.typecheck` array and reaches for this only when the array is absent. With neither configured, `push` asks rather than guessing a build command. Configuring only the combined form works; configuring both means the array wins. |
| `verify.test` | string | none | Your standard test suite. Green is a gate. If some suites are deliberately excluded from it (see `skipDuringStoryBuilds` and `preShipChecks`), exclude them *here* too, so a later generic test step cannot accidentally pull one in. **Leaving it unset is a real hazard under fast develop mode** — see the warning below. |
| `verify.testSingle` | string | none | How to run one spec file, for the tight build loop. Write it with a `<path/to/test.spec.ts>` placeholder. |
| `verify.lint` | string | none | The linter, run when the diff touches the paths it covers. |
| `verify.testDir` | string | none | Where tests live, so the build engine knows which mirrored directory a new spec belongs in. |
| `verify.skipDuringStoryBuilds` | array | `[]` | Slow **cloud CI** suites that are too expensive to run per item, each mapped to its applicability rules and CI check names. Empty — the shipped default — means there is nothing to compute: no PR ever waits on such a check, and an absent check is settled rather than pending. Entry schema below. |

::alert{type="danger" title="No `verify.test`, plus fast develop mode, means merged code with no mechanical gate at all"}
Fast develop mode is **on by default**, and under it an item on an integration branch gets no pull request, no cloud reviewer and no CI — the local suites are its *only* mechanical gate, which is precisely why `fastStoryMerges.requireLocalVerifyGreen` defaults to `true`.

If `verify.test` is unset there is no suite for that gate to run. The item is still reviewed by the local engines (nothing silently skips a review), but nothing mechanically verifies it before it merges onto the integration branch — and the first thing that does is the release pull request, by which point there are N items of accumulated diff to bisect through.

Do one of two things before running the loop on real work: **configure `verify.test`**, or **set `epicIntegrationBranches.fastStoryMerges.enabled: false`** so every item goes back to its own pull request and CI. Do not leave both unset and enabled.
::

### `verify.skipDuringStoryBuilds` entries

Each entry names one slow cloud suite and declares exactly when its check is mandatory. The four fields are the whole schema — the procedure that consumes them is `slow-suite-gating.md` in the `review` skill's own references:

```json
{
  "name": "e2e-matrix",
  "alwaysRunWhenBase": ["productionBranch"],
  "manualTriggerLabel": "run-e2e",
  "runWhenChangedPaths": ["apps/web/**", "packages/e2e/**"],
  "ciChecksByBase": {
    "baseBranch": ["E2E (PR gate)"],
    "productionBranch": ["E2E (full matrix)"]
  }
}
```

| Field | Shape | What it means |
|---|---|---|
| `name` | string | How the suite is reported. |
| `alwaysRunWhenBase` | string[] | Bases where the suite is mandatory **unconditionally, paths irrelevant** — typically `productionBranch`. This case short-circuits everything else: a docs-only or frontend-only release still runs the full suite, and that guaranteed run at the production boundary is exactly what earns the development-side path filter its narrowness. |
| `manualTriggerLabel` | string | The pull-request label that forces the suite on for one run. **The label is the mechanism, not the instruction:** your workflow cannot see that someone asked for the suite, so the loop *adds the label* (`gh pr edit <pr> --add-label <label>`) before the ready-flip. Ask for the suite without materializing the label and its check never runs, so the settle loop waits on it forever. |
| `runWhenChangedPaths` | string[] | Glob patterns — not literal strings — matched against the complete, SHA-pinned final changed-file set, with renames matched on **both** source and destination. Match none of the three cases and the suite is non-applicable: omitted completely, its absent check expected rather than pending. Under a well-scoped filter that is the *common* outcome. |
| `ciChecksByBase` | `{base: string[]}` | The CI check names to require, keyed by base — `baseBranch` and `productionBranch` resolve to your configured branches. Only the checks mapped to *this* PR's base are required; checks mapped to another base are expected to skip. **A base with no mapping is an item-level exemption**: an item PR into an integration branch does not wait on the suite even when its own diff matches, because the accumulated release diff is evaluated afresh when the integration branch targets `baseBranch`. |

::alert{type="warning" title="Every entry needs a matching workflow job, changed in the same commit"}
These fields must mirror your own workflow's triggers exactly. Add, remove or narrow a case here without changing the workflow in the same change and you get one of two silent outcomes: the loop waits forever on a check that never runs, or it merges without a gate that should have fired. That is also why the shipped default is `[]` — most repos have no slow cloud suite, and an empty list means there is simply nothing to compute.
::

::alert{type="warning" title="A slow suite belongs in exactly one of two lists"}
`verify.skipDuringStoryBuilds` is for suites that run in **cloud CI** but are gated to fire only on certain pull requests; every entry needs a matching workflow job, or the loop waits forever on a check that never runs. `preShipChecks` is for suites that run **locally, at the ship boundary, and never in CI**. Listing the same suite in both makes it run twice; listing it in neither means nothing validates it at all. If you ever move a suite from CI to local, add its `preShipChecks` entry and delete its `skipDuringStoryBuilds` entry *and* its workflow job in the same change.
::

### `preShipChecks`

Local suites the repo deliberately keeps out of the pipeline. Absent or `[]` makes the pre-ship steps explicit no-ops. Each entry:

```json
{
  "name": "integration-suite",
  "pathGlobs": ["packages/api/**", "migrations/**"],
  "command": "pnpm test:integration",
  "when": "perPr",
  "timeoutNote": "~25 min. Runs in the background with a long timeout; never concurrently with another test run."
}
```

| Field | Shape | What it means |
|---|---|---|
| `name` | string | How the check is reported. |
| `pathGlobs` | string[] | Which changed files select this check on a per-PR run. An **empty array runs it on every** pull request at that point. On a `releaseOnly` entry the globs are deliberately ignored. |
| `command` | string | What to run. |
| `when` | `"perPr"` \| `"releaseOnly"` \| `"always"` | `perPr` runs at the PR boundary when the final diff matches; `releaseOnly` runs **unconditionally** at the release boundary; `always` runs at both. |
| `timeoutNote` | string | Free prose surfaced to the operator before the run — expected duration, container/serialization caveats. This is where a repo's operational lore belongs, so the schema stays flat. |

Semantics worth knowing: matched checks run **sequentially, in array order** with no de-duplication (two entries matching the same diff both run, deliberately), in the background with a long timeout, and never concurrently with another test run. **A red check blocks the ship.** Only at the release boundary may the owner explicitly waive one, and the waiver is recorded in the release report. A `pathGlobs` entry exists precisely because a change there breaks the check invisibly — narrowing the globs to skip a run defeats the point.

## Review

The `review.*` block is the engine roster and the review-then-CI ordering. See [the delivery loop](/developer-experience/agentic-skills/claude-skills-delivery-loop) for the reasoning.

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `review.localCommand` | string \| null | `null` | A local review CLI run on every change, in the worktree. `null` is legal and means "no second local engine" — Claude's adversarial pass is then your only local gate. Include a `<base>` placeholder for the base ref. The engine is on the roster only if this is non-null **and** its first token resolves as a binary; a configured-but-missing binary is reported as a degradation of that run, not silently dropped. Example below. |
| `review.localReviewerName` | string | `"Codex"` | The human name for whatever `localCommand` runs. **It is read**, by `review`, when it announces the resolved roster ("engines this run: Claude + Codex + Copilot") and whenever it attributes a finding to the local engine. Set it to match your CLI: a repo running something other than Codex must not have its reviewer announced as Codex. |
| `review.automatedReviewers` | array | none | Cloud reviewers requested on each pull request. `[]` is legal and means no cloud wave: nothing is requested, polled, or resolved, and absent reviews are *correct*, not pending. |
| `review.openPullRequestsAsDraft` | boolean | `true` | Open PRs as drafts so no workflow fires while the reviewers work. |
| `review.readyForReviewReleasesCi` | boolean | `true` | Marking the PR ready is the deliberate act that starts CI. |
| `review.ciHeldUntilReviewSettled` | boolean | `true` | The contract the two flags above implement. All three `false` describes a CI-runs-on-draft repo: PRs open non-draft, there is no ready-flip, and CI settles concurrently with review. Mixed values are unsupported-but-safe — the skills take the strictest configured reading and say so. |
| `review.reviewDepthPolicy` | string | none | Prose stating the no-skip rule: every configured engine runs on every PR at maximum effort, and what scales with risk is the *breadth* of the fan-out, never whether a pass happens. |
| `review.pollTimeoutMinutes` | number | `20` | Bound for the **cloud-reviewer** discovery poll only. On expiry the loop proceeds with the findings in hand and records which reviewer never answered. A CI wait is bounded separately and re-launched if it outlasts this. |
| `review.resolveAddressedThreads` | boolean | `true` | Reply to and resolve every addressed review thread. Findings in a review *body* (which have no thread) are reported regardless — this flag governs threads only. |
| `review.notifyWhenSettled` | boolean | `false` (absent is read as off) | Whether a standalone review notifies you when the PR is finally ready. |

### An example `review.localCommand`

There is no shipped command — the plugin has no idea what review CLI you run — so this is an **example**, not a default. It is the one DevStride's own repository uses, with a locally installed [Codex](https://developers.openai.com/codex/cli) CLI:

```json
"localCommand": "codex exec review --base <base> -c model_reasoning_effort=\"xhigh\""
```

Three things to copy from the shape rather than the specifics: the `<base>` placeholder, which the skill substitutes with the base ref it is reviewing against; a flag pinning the CLI to its **maximum** reasoning tier, because the review-depth contract is max effort on every pull request; and a command that writes its findings to stdout and exits, since the skill runs it in the background and reads what it printed. If your CLI has its own MCP or tool integrations that would stall on an interactive prompt, disable them here — a review that hangs looks identical to a review that found nothing.

### An `automatedReviewers` entry

Each entry describes one bot precisely enough to request it without guessing:

```json
{
  "name": "Copilot",
  "bot": "copilot-pull-request-reviewer[bot]",
  "how": "requested_reviewer",
  "value": "copilot-pull-request-reviewer[bot]",
  "graphqlBotId": "BOT_kgDOCnlnWA"
}
```

`how` tells the skill the mechanism to use; `graphqlBotId` is needed because GitHub's REST review-request endpoint rejects bots outright (`Reviews may only be requested from collaborators`), so the request goes through a GraphQL mutation that takes node IDs. The skills **iterate this array** and request each entry per its own `how` — a repo with two reviewers gets both, and hardcoding one would leave the other never asked while the poll still waited it out.

::alert{type="info" title="How to find a `graphqlBotId`"}
Request the reviewer **once by hand** on any pull request (the reviewers box in the GitHub web UI), then read the node ID straight off that pull request's timeline:

```bash
gh api "repos/<owner>/<repo>/issues/<pr>/timeline" --paginate --slurp \
  | jq -r '.[][] | select(.event == "review_requested")
           | [.requested_reviewer.login, .requested_reviewer.node_id] | @tsv'
```

The `node_id` column is the value to paste into `graphqlBotId`. It is stable per bot, so you look it up once. For Copilot's reviewer it is `BOT_kgDOCnlnWA`.

**Do not discover it from GitHub's `suggestedActors` query.** That query lists candidates for *assignment*, and for Copilot it returns `copilot-swe-agent` (`BOT_kgDOC9w8XQ`) — the coding agent, a completely different bot from the reviewer. Requesting the coding agent is accepted without error and creates no review request at all, so the loop then waits out its poll on a reviewer nobody asked.
::

## Pull request body, commits, and conventions

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `prBodyTemplate.sections` | `{heading, guidance}[]` | four DevStride sections | The PR body's section list, rendered **in order**, each filled per its `guidance`. The list is ordered and **closed** — no invented extra headings. A caller's flavour (epic release, hotfix, production release) changes how sections are *filled*, never the section set. |
| `prBodyTemplate.noAiAttribution` | boolean | `true` | No AI-attribution text in PR **bodies**. Commit trailers are a separate matter and are session-scoped, never configured here. |
| `commitConventions.messageFormat` | string | Conventional Commits with an item tag | The shape of an ordinary commit. The `<itemTag>` inside it renders per `itemTagFormat` below — don't restate the tag shape here, or the two drift. |
| `itemTagFormat` | string | `"[I#####]"` | **How a work item is cited in a commit message** — and the key that makes the loop portable to a tracker that isn't DevStride. It is read by `push` when it writes the commit and by the build engine when it commits as it goes. The shipped default is DevStride's own numbering; a repo tracking work as `PROJ-123` sets `"[PROJ-123]"` and its commits read natively. The tag is added **only when the work actually has an item** — a merge or a repo chore keeps a meaningful conventional message with no tag — and a number is **never composed to satisfy the format**. |
| `commitConventions.reviewFixFormat` | string | `fix(<scope>): <summary> [<itemNumber> review]` | The shape of a commit that lands a review finding. |
| `commitConventions.epicMergeFormat` | string | `merge: <itemNumber> [<N>] <short scope> into <epic-slug> integration` | The shape of a fast-mode story's merge onto its integration branch. These merges are read back to build the release PR body and the remaining-work counts, so their legibility is functional. |
| `conventionsDoc` | string | `"AGENTS.md"` | **Your** coding-standards file. The build engine reads it and obeys it — this is the single key that most decides whether the loop writes code that looks like yours. It stays human-owned; nothing in the loop writes to it. |
| `preCommitWiringChecks` | string[] | none | Repo-defined checks the build loop expects to pass before each commit (typically enforced by your git hooks). Absent means the repo configures none. |
| `lessonsDoc` | string | `".claude/ds-lessons.md"` | The per-repo lessons store — review findings distilled into a small, capped, curated file. `review` is the only skill that writes it; the build engine reads it as **advisory hypotheses**, never rules. An absent or empty file is a valid state everywhere. |

::alert{type="warning" title="The lessons store must be a committed file"}
It is repo data, not scratch state — if it is not committed, every lesson the loop distils is silently lost. Repositories commonly gitignore `.claude/`, so check that the path you configure is not ignored (`git check-ignore <path>` should exit non-zero) before relying on it.
::

## Hierarchy roles

How your organization's work-type names map onto the two roles the delivery skills reason in.

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `hierarchyRoles.releaseUnit` | string \| null | resolved at runtime | The container type whose completion cuts a release — the level that gets an integration branch and a release PR. |
| `hierarchyRoles.leaf` | string[] \| null | resolved at runtime | The executable, roughly-one-day item types the loop selects and ships. |

Absent or `null` for either role, the skills resolve **both** from `get_work_type_hierarchy` on every run: leaf = the bottom, childless levels; release unit = the container level directly above them. Roles bind to **function, not depth** — a shallower or deeper hierarchy simply has fewer or more container tiers above the release unit. If either role is genuinely ambiguous (parallel bottom levels, several candidate containers) the loop asks once and suggests recording the answer here.

::alert{type="danger" title="A configured role that no longer exists is a hard stop, not a fallback"}
If no ancestor matches a **configured** `releaseUnit`, the loop first validates that the configured type still exists in your hierarchy. A renamed work type or a typo must stop and ask — silently concluding "no release unit" would route every story straight to `baseBranch`, bypassing integration batching entirely and putting unbatched work on a branch that is promoted to production.
::

## CI

Descriptive facts about how your pipeline is held around the draft/ready flip, so skill prose can cite config instead of hardcoding your workflow.

| Key | Shape | What it controls |
|---|---|---|
| `ci.workflowGlobs` | string[] | Where your workflow files live, for any skill reasoning about them. |
| `ci.draftGateCondition` | string | The expression every workflow job is gated on — e.g. `github.event.pull_request.draft == false`. Purely descriptive: the gate lives in your workflows, this key just names it. |
| `ci.gateJobName` | string \| null | A cheap, path-filter-free job whose non-`skipping` conclusion **proves the draft gate actually opened**. With `null`, the skills instead verify the flip by the appearance of a new workflow run for the head SHA. |

That gate-job check exists because the failure it catches is invisible: flipping a PR ready in the same breath as a push can leave every job reporting `skipping`, which renders identically to a suite being legitimately non-applicable. A skipped board read as a green one is a merge with no CI behind it.

## Release

| Key | Shape | Default | What it controls |
|---|---|---|---|
| `release.productionBranch` | string | `"master"` | The branch a production release merges into. |
| `release.releaseSource` | string | `"develop"` | The branch promoted from. A PR with this head and that base is detected as **the release** and handed to `/devstride:release` rather than treated as an incremental PR. |
| `release.autoDeployOnMerge` | string | none | Plain-English description of what merging to production triggers. The skill **quotes this back to you** at the go-ahead gate rather than assuming any particular deploy provider. |
| `release.docsRepo.path` | string | none | Path to a sibling documentation repository (`~` is expanded). Absent `docsRepo` means the repo has no docs sibling and the documentation phase is skipped entirely. |
| `release.docsRepo.branch` | string | none | The branch the docs pass commits to. |
| `release.docsRepo.autoDeployOnPush` | boolean | none | Whether pushing that branch publishes the docs site — i.e. whether the docs commit is an outward-facing action. |
| `release.docsRepo.updateByDefault` | boolean | none | Whether a release updates the docs by default. You can still suppress it per-release by passing `no docs` (or `skip docs`). |
| `release.docsRepo.releaseNotesWhen` | string | none | The condition under which a release also writes a new release note, e.g. "the delta is large AND user-facing". |

The release skill discovers the docs repository's *structure* — its nav config, section directories, where release notes live — from the repository itself, and derives internal link forms from a known-good existing page rather than composing them. Nothing about your docs layout belongs in this config.

## Which keys are only prose

It is worth being precise here, because "that key is just documentation" is an easy thing to assume and an expensive thing to get wrong. Three categories:

- **Read and acted on.** Almost everything in this file. Change it and the loop behaves differently.
- **Read and quoted, but describing something that lives elsewhere.** `ci.draftGateCondition` names the condition your workflows are gated on; `review.reviewDepthPolicy` states the no-skip rule; `release.autoDeployOnMerge` says what a production merge triggers. Skills read these and repeat them back to you — at the release go-ahead gate, in the roster announcement — so a stale one produces a confidently wrong statement. Editing them does not change the underlying behaviour, but it does change what you are told about it.
- **Genuinely inert.** Exactly one: **`epicIntegrationBranches.example`**, a sample branch name kept beside the pattern so a reader can see what the pattern produces. Nothing reads it.

Three keys are commonly mistaken for the last category and belong in the first:

- **`epicIntegrationBranches.slugRule` is read** — `build-item` uses it to name a new integration branch. Leave it inconsistent with your naming and two sessions can invent two different branches for the same release unit.
- **`review.localReviewerName` is read** — `review` announces the roster with it and attributes local findings to it. Leave it at the default while running a different CLI and every report names the wrong reviewer.
- **`itemTagFormat` is read** — by `push` and by the build engine, on every commit that cites an item. It is the key that ports the loop to a non-DevStride tracker; it is not decoration.

And two keys older configs carry **no longer exist**: `review.localReviewEffort` and `generated.regeneratedByPreCommitHook`. Both were removed. The effort flag was always carried inside `localCommand` itself, so a separate key was only ever a second place to disagree. The pre-commit-hook key was worse than redundant — it was substantively false: a pre-commit hook of that kind runs formatting and wiring checks and regenerates **nothing**, so a skill trusting it would skip regeneration and ship stale generated artifacts. Delete them if you find them; do not reintroduce either.

::alert{type="warning" title="Both directions of the walk are load-bearing"}
An absent JSON key does not error. The skill reads nothing and improvises, and the improvisation looks like a decision. So when you add or rename a key, check it **both ways**: every key a skill cites should exist in your file, and every key in your file should have a skill that honours it. A key you believe is driving behaviour while nothing reads it is exactly how the `regeneratedByPreCommitHook` mistake above stayed plausible for so long.
::
