## What a variable is

A variable is **a question the template asks when it is applied**, plus the
slots in the template that get filled with the answer.

Nothing more mysterious than that. You declare *Customer name* once; four node
titles and five descriptions reference it; the person applying the template
types "Northwind Trading" once and all nine places fill in.

Without variables a template is a rubber stamp that always produces identical
items. With variables it becomes a *form* that produces the right items.

## A worked example

Everything on this page is illustrated with one template — **Customer
Onboarding Programme**. Its shape is fixed: a workstream, an epic under it, and
four features (kickoff, data migration, training, go-live), each with sub-items.
What changes per customer is captured in six variables.

![The variables panel showing six variables: customer_name, go_live, onboarding_team, success_manager, training_tier and seats](/images/templates/example-variables-panel.png)

Read one card and you can read them all:

* **`customer_name`** is the variable's **name** — the identifier you type
  inside a `{{token}}`. It must be unique, and may use letters, numbers and
  underscores only.
* **TEXT** is its **type**, which decides what kind of answer is accepted and
  where the variable may be used.
* **Label: Customer name** is the human wording shown on the apply form. If you
  leave it blank, the raw name is shown instead — so always write one.
* **REQUIRED / OPTIONAL** — click the pill to flip it. A required variable
  blocks apply until it is answered; an optional one may be left blank, and the
  fields bound to it are simply left unset.
* **used in 2 titles · used in 5 descriptions** — a live usage tally. A variable
  with no usage is dead weight and is obvious at a glance.

## The eight types

Add one with **+ Add variable** at the foot of the panel. A template may declare
up to **20**.

![The Add variable menu listing Date, User, Team, Board, Text, Number, Options and Custom field](/images/templates/builder-variable-types.png)

| Type | Asks for | Bind it to |
| --- | --- | --- |
| **Date** | A calendar date | Start date / Due date (with an offset) |
| **User** | A person | Assignee |
| **Team** | A team | Team |
| **Board** | A board or cycle | Board |
| **Text** | A line of text | Titles and descriptions |
| **Number** | A number | Titles and descriptions |
| **Options** | One value from a list you define | Titles and descriptions |
| **Custom field** | A value valid for one specific custom field | That custom field |

Two of these deserve a note.

**Options** owns its list. Unlike every other reference in a template, the
choices are not org configuration — you type them into the variable itself as
chips, with **+ option**. An Options variable needs at least **2** and allows up
to **50**. Use it when the answer must come from a short, template-specific menu:
*Standard / Premium / Enterprise*, *EU / US / APAC*, *Bronze / Silver / Gold*.

**Custom field** is declared *for* a particular field, chosen when you add the
variable (the menu offers your eligible fields as a submenu). It then reads that
field's own options, bounds and roster when the template is applied — so it can
never drift out of step with the field it fills.

## Fixed vs Variable, field by field

Variables only do anything once a node **binds** to one. Every bindable field in
the node inspector carries a **Fixed / Variable** toggle:

* **Fixed** — the field shows its normal picker and stores a literal value.
* **Variable** — the field shows a list of variables *of the matching type* and
  stores a reference.

![A Feature node bound to variables: dates anchored to go_live, team and assignee bound to variables](/images/templates/example-node-inspector.png)

That type-matching is not cosmetic. A **Team** field only offers Team variables;
an **Assignee** field only offers User variables. You cannot accidentally point a
date field at a text answer.

## Tokens in titles and descriptions

Titles and descriptions are text, so they don't bind to a single variable —
they **interpolate** one or more.

Flip **Title** to **Variable** and a row of **Insert** chips appears, one per
usable variable. Click a chip to drop its token at the cursor, or type the token
yourself:

```
{{training_tier}} training
```

Applied with *Premium*, that node is created as **Premium training**.

Descriptions work identically. In the example template the workstream
description reads:

> Everything Acme does to bring **{{customer_name}}** live — kickoff, data
> migration, {{training_tier}} training and the go-live sign-off.

::alert{type="warning" title="Only four types can be interpolated"}
Tokens accept **Text, Number, Date and Options** variables — the ones that
resolve to text. **User, Team and Board variables resolve to records**, not
strings, so they cannot be written into a title or description. They are bound
to their own fields instead. The builder shows only the eligible variables as
Insert chips, and says so in the hint beneath.
::

The tally on each variable card (*used in 2 titles*) counts these tokens, so you
can always see whether a token you typed by hand actually matched a variable —
a typo shows up as a usage count that didn't go up.

## Dates: one answer, a whole schedule

This is the highest-value thing variables do, and the least obvious.

A date field in Variable mode stores **a date variable plus an offset in days**.
Every node in the template can anchor to the *same* variable at a *different*
offset — so answering one date lays out the entire plan.

In the example, every node anchors to `go_live`:

| Node | Start | Due |
| --- | --- | --- |
| *(workstream)* Onboarding | `go_live − 45` | `go_live + 5` |
| Kickoff & discovery | `go_live − 45` | `go_live − 35` |
| Data migration | `go_live − 35` | `go_live − 14` |
| Premium training | `go_live − 14` | `go_live − 5` |
| Go-live & sign-off | `go_live` | `go_live + 5` |

The inspector spells each one out in words — *Resolves to go_live − 14 days when
the template is applied* — so you never have to hold the arithmetic in your head.

Answer `go_live = Nov 16` and the whole programme dates itself backwards from
mid-November. Answer a different date next quarter and it re-lays itself out.

::alert{type="tip" title="Anchor to the date people actually know"}
Anchor to the date the business commits to — the go-live, the launch, the
release, the sprint start — not to "today". People know when the customer goes
live; they do not know when the data-migration workstream ought to begin. That
is what the offsets are for.
::

## Scoping a person to a team

A **User** variable can be **scoped**, which constrains who may be picked. The
`Scoped to` row on the card offers:

* **Anyone in the organization** — no constraint.
* **A named team** — always that team, whoever applies the template.
* **Another Team variable** — the powerful one: *whichever team is chosen when
  the template is applied*.

In the example, `success_manager` is scoped to `{{onboarding_team}}`. The card
notes *— filled before this one*, and the apply form honours it: choosing the
team first narrows the person list to that team's members, and the form says so
in as many words.

![The apply form showing the assignee list filtered to Service Team members only](/images/templates/apply-scoped-assignee.png)

> Showing 2 of 98 — Service Team members eligible for this slot.

Two people out of ninety-eight. That is the difference between a form somebody
fills in correctly and a form somebody guesses at.

Scoping also protects the result. An assignee who is not in the item's team is
**silently dropped** when the item is created — the inspector warns about this
on any node where it could happen. A scoped user variable makes that failure
mode unreachable.

## Designing a good set of variables

A short checklist that separates templates people reuse from templates people
abandon.

**Make variable of what actually changes.** If every launch is run by the same
team, fix the team. Asking a question whose answer is always the same is noise.

**Prefer one anchor date to many.** One `go_live` with offsets beats five
separate date questions, and it stays correct when the plan slips.

**Scope every person question.** Almost every user variable should be scoped to
a team variable. It shrinks the picker, and it prevents assignees that will be
dropped.

**Use Options rather than Text for a closed set.** *Training tier* has three
legal answers; a free-text box invites "premium", "Premium ", and "prem".

**Write labels, not identifiers.** The apply form shows `Customer success
manager`, not `success_manager`. The person filling it in has never seen your
template before.

**Mark genuinely optional things optional.** In the example, `seats` is optional
— an onboarding with an unknown seat count should still be able to start. Every
required variable is a way for someone to get stuck.

**Watch the usage tallies.** A variable reading no usage is either a leftover or
a token you mistyped. Both are worth ten seconds.
