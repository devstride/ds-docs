## Two ways to start

**Start from scratch.** On the **Templates** page, click **New Template**. You
get an empty builder.

![The template builder with an empty structure, no node selected and no variables](/images/templates/builder-new-empty.png)

**Start from work that already exists.** If you have already built the thing
once by hand, capture it instead of retyping it — see
[Capture an existing tree](#capture-an-existing-tree) at the end of this page.
For most people this is the faster route: build it once for real, capture it,
then replace the specifics with variables.

## The three panes

The builder is one screen with three panes. It is worth learning what each pane
owns, because every task in this guide is "do something in one of these three".

![The builder showing the structure tree, node inspector and variables panel for the Customer Onboarding Programme template](/images/templates/example-builder.png)

| Pane | Owns |
| --- | --- |
| **Structure** (left) | The **shape** — which nodes exist, of which type, nested how. |
| **Node** (middle) | The **fields** of whichever node is selected on the left. |
| **Variables** (right) | The **questions** the template will ask when it is applied. |

Above them sits the template's own header — **Template name**, **Description**,
its **Audience** with a **Share…** button, and **Applies to**, which is
computed for you from the root node's type.

At the bottom: **Cancel**, **Preview** and **Save Template**. Changes are held
in the builder until you save; the header reads *All changes saved* or
*Not saved yet* so you always know which.

::alert{type="warning" title="Preview and Apply need a saved template"}
Both buttons act on the **stored** definition, so they are disabled while the
draft is unsaved — with a tooltip saying so. Save first, then preview.
::

## The Structure pane

The tree is the template's skeleton. Its header shows a running count —
`6 nodes · depth 3` — against the limits: a template may hold at most **500
nodes** and nest at most **10 levels** deep.

Each row carries, left to right: a drag handle, an expand chevron, a **type
chip** (Workstream / Epic / Feature / Story / Sub-item, tinted like your work
types), the title, and a small `{ }` badge showing **how many variables that
node uses**. Hover a row for its three actions:

* **+ (Add child)** — opens a menu headed *Add under &lt;type&gt;* listing only
  the node types that are **legal** beneath this one, plus **Sub-item** for work
  items. If nothing may go there, the menu says so rather than offering an
  option that would be rejected on save.
* **Duplicate node** — copies the node and everything under it.
* **− (Remove node)** — deletes the node and its subtree.

At the bottom of the tree, **Add sibling** (or **Add root** when the tree is
empty) adds a top-level node. Drag the handles to reorder.

::alert{type="note" title="All roots must be the same kind"}
A template's top level is either **all workstreams** or **all work items of one
work type** — never a mixture. That single rule is what makes "Applies to"
answerable, and therefore what lets DevStride tell you up front whether a
template can be dropped where you are pointing.
::

### Legal children, and why the menu is short

The **Add child** menu is filtered by your organization's work-type ladder. If
your ladder says a Story sits under a Feature, then a Feature node offers Story
(and Sub-item) — not Epic. The builder only ever lets you author something the
save would accept, so you find out about an illegal shape while you are drawing
it rather than at the end.

## The Node pane

Select any row on the left and the middle pane fills with that node's fields.
Which fields appear depends on what kind of node it is — a workstream has a
colour and no assignee; a sub-item inherits its parent's team and so is never
asked for one.

![The node inspector for a Feature node, showing title, description, dates, team, assignee, board, priority, tags, point effort and custom fields](/images/templates/example-node-inspector.png)

Reading down a work-item node:

* **Title** — with a **Fixed / Variable** toggle. In Variable mode you can weave
  `{{token}}` placeholders into the text; see [Variables](/workspace-administration/templates/variables#tokens-in-titles-and-descriptions).
* **Description** — rich text, with the same Fixed / Variable toggle and the same
  token support. In Fixed mode the description is copied verbatim onto every
  item created from the node.
* **Start date** and **Due date** — Fixed (a literal date) or Variable (a date
  variable **plus an offset in days**). Offsets are what let one answered date
  drive an entire schedule.
* **Team** — Fixed (a named team) or Variable (a team variable).
* **Assignee** — Fixed (a named person) or Variable (a user variable). If the
  node's team is set, the builder warns that an assignee outside that team is
  silently dropped when the item is created.
* **Board** — four modes. **None** leaves the item off any board. **Fixed** pins
  one specific board. **Variable** lets the person applying choose. **Cycle**
  resolves to whichever cycle is open on a chosen cadence at apply time
  (optionally offset by ±1 cycle), so the template follows the cadence instead
  of pinning to one sprint forever.
* **Priority**, **Tags**, **Point effort**, **Estimates (hours)** — plain values.
  Point effort and estimates only appear if the work type has them enabled.
* **Custom fields** — every custom field eligible for this work type, with a
  tally (*0 of 3 set*) and its own Fixed / Variable toggle per field.

Workstream nodes swap the work-item fields for a **Colour** picker. Sub-items
carry only a title, description, dates and an assignee.

## The Variables pane

The right pane is the list of questions the template will ask. Because it is the
single most important idea in the feature, it has [its own
page](/workspace-administration/templates/variables) — read that next.

## Saving

**Save Template** validates the whole definition on the server before storing
it: work types exist, priorities belong to their work type's collection, teams
and users are real, point effort is a whole number where required, variable
names are unique, and the caps are respected. If something is wrong you get a
message describing it and nothing is saved.

Template names must be unique **per author** — you and a colleague may each own
a template called *Sprint Setup* without colliding.

## Capture an existing tree

If the work already exists in DevStride, don't retype it.

Right-click any workstream or item — in the Map, the items table, or its drawer
— and choose **Save as Template…**.

![The item context menu showing Apply Template and Save as Template entries](/images/templates/entry-point-item-menu.png)

The dialog names the source, pre-fills a template name, and tells you exactly
what will and will not be captured.

![The Save as Template dialog showing the source item, template name, private audience and what will be captured](/images/templates/save-as-template.png)

**Captured:** titles, descriptions, work types, dates, assignees, teams,
priorities, tags, estimates, point effort, sub-items and custom-field values,
for the item and everything beneath it.

**Not captured:** calculated and Service Desk fields, statuses, boards,
comments, attachments and relationships.

::alert{type="tip" title="Capture, then generalise"}
Everything captured is saved as a **fixed** value — a snapshot, not yet a
template in the useful sense. The dialog says so, and **Save & open builder**
drops you straight into the builder to do the second half: swap the literal
start date for a date variable, swap the named assignee for an assignee slot,
swap the customer's name in the title for a `{{token}}`. That two-step —
capture, then generalise — is the fastest way to a good template.
::

New templates, however you create them, start **Private**. Nobody else can see
them until you [share](/workspace-administration/templates/sharing-templates)
them.
