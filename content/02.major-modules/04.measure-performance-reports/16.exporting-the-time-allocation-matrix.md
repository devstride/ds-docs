## Why export

The on-screen grid is for exploring. The export is for handing over — to finance for capitalization, to a client with an invoice, or into your own spreadsheet for further modelling.

The workbook contains **every row**, including branches you had collapsed on screen, laid out with proper Excel outlining so recipients can expand and collapse it themselves.

## Starting an export

1. **Run the report first.** Export works from results, so it stays disabled until you have some. If it is disabled, the tooltip tells you why — *Run the report before exporting.*, *Rerun the report before exporting.*, or *Wait for the report to finish.*
2. Click **Export** in the toolbar.
3. In **Export Report to Excel**, fill in **Export Name**. It pre-fills with your saved view's name, or *Time Allocation Matrix*. This becomes the workbook's title row and the downloaded filename, so name it for whoever receives it — *Q1 2026 Capitalization* travels better than *Time Allocation Matrix*.
4. Note the footer: *Every row in this report snapshot will be exported to an Excel workbook, including rows currently collapsed on screen.*
5. Click **Export Report**.

DevStride takes you to **Analyze → Exports**.

## Downloading it

The export runs in the background. In the **Exports** list your job appears with a **Running** badge; when it finishes, **click its name to download** the `.xlsx`.

It is **not emailed** — you collect it from the Exports tab whenever it is ready. Large reports take a little time; you can leave the page and come back.

If the job shows **Failed** or **Timed Out**, start it again. A repeated failure usually means the report is very large — narrow the scope and re-run.

## What the workbook contains

A single worksheet named **Allocation Matrix**.

**Row 1** — the export name, as a title bar.

**Row 2** — a provenance note recording exactly what this is:

> Snapshot as of 11 Aug 2026, 09:14 America/New_York. Report timezone: America/New_York. Date range: Jan 1, 2026 through Mar 31, 2026. Metric: Actual Time (hours).

Any warnings from the run are appended here too — a partial period, or a note that some configured selections were unavailable. **This row is why the export is safe to send onward**: the recipient can see when it was taken, in which timezone, and over what range, without having to ask.

**Row 3** — the header row: one column **per hierarchy level**, then one per month, then **Range Total** and **Total %**.

**The body** — detail rows, plus a **subtotal** and an **allocation** row for every parent branch, ending in **Grand total**.

### Differences from the on-screen grid

Two, both deliberate:

| On screen | In the workbook |
|---|---|
| One indented hierarchy column | **One column per level** — so you can filter, pivot, and group in Excel |
| Only expanded rows | **Every row**, with Excel outlining to collapse them |

The multi-column layout is what makes the export useful as data rather than a picture. You can pivot on level 1, filter to a single epic, or feed the columns straight into another model.

### Other details

- **Archived items** have ` (Archived)` appended to their title.
- **Direct time** becomes an Excel **cell comment** on the Range Total cell: *"Includes 12.50 hours logged directly to Platform Migration that are not represented by child rows."*
- Hours are formatted `0.00`, percentages `0.00%` — real numbers, not text, so they calculate.
- Panes are frozen at the hierarchy columns and header row.
- Print setup is landscape, fit to width, with the header repeating on every page.

## The snapshot model

This is the part worth understanding, because it explains the one error people hit.

Running the report creates a **snapshot** — a point-in-time capture of the results, belonging to you, that lives for **30 minutes**. The export renders from that snapshot rather than re-querying, so **the workbook matches exactly what you saw on screen**. It cannot drift because someone logged time while the export was running.

The trade-off is that the snapshot expires. If you leave the report open too long and then export, you get an amber banner:

> Run the report again before exporting. The current results will remain visible until you rerun.

Click **Rerun report** and export again. Your results stay on screen in the meantime, so you do not lose your place.

::alert{type="tip" title="Export while the numbers are fresh"}
If you are producing a report for someone else, run it and export it in the same sitting. The provenance row then carries a timestamp minutes old, which is exactly what a reviewer wants to see.
::

## Access is re-checked at export time

Item permissions are verified again when the export runs, not only when you ran the report. If you lost access to something in the meantime, the export fails with *"You no longer have access to this report execution."*

This means an export can never contain items you are not currently entitled to see, even if you could see them when the snapshot was taken.

## Troubleshooting

| Message | What to do |
|---|---|
| *Run the report before exporting.* | Run the report first; export needs results. |
| *Run the report again before exporting.* | The 30-minute snapshot expired. Click **Rerun report**. |
| *The export could not be started. Try again.* | Transient. Retry; if it persists, narrow the report. |
| *This report export can no longer be downloaded. Rerun the report and generate a new export.* | The stored file expired. Re-run and export again. |
| *You no longer have access to this report execution* | Your item access changed. Re-run the report to see what you can access now. |
| **Failed** or **Timed Out** in the Exports list | Usually size. Narrow the scope or shorten the range and try again. |
