---
title: "Variables"
description: "Variables are the questions a template asks when it's used. They're what turns one rigid copy into a template that serves every client, every quarter, every team."
---

Without variables, a template is a photocopy: apply it and you get "Onboarding" and "Kickoff workshop" every single time, with the same dates and the same person assigned, and you spend the next ten minutes editing.

A **variable** is a question the template asks at the moment you apply it. You answer it once, and DevStride threads that answer through every node that needs it.

::alert{type="tip" title="Variables are optional"}
If your template is a fixed checklist that doesn't need to ask anything, you can switch the whole system off with the **Variables** toggle in the builder and skip this page — see [Simple mode](/major-modules/item-templates/building-a-template#simple-mode). New templates start that way.
::

## The idea in one example

Suppose the workstream title is set to:

```
{{Client}} onboarding
```

`{{Client}}` is a **token** — a placeholder pointing at a variable called `Client`. When someone applies the template, DevStride asks:

> **Client name** · `Northwind Bank`

…and creates a workstream called **Northwind Bank onboarding**. Apply it again next week for a different client and you get **Acme Savings onboarding** from the same template. One template, unlimited clients.

The same variable can be used in as many places as you like. Answer once, and the client's name lands in the workstream title, the kickoff feature title, and the description — all at the same time.

## Adding a variable

Variables live in the right-hand panel of the builder. If you can't see it, turn the **Variables** switch on — it's next to **Try it**, above the panes. Then click **+ Add variable** and choose a type.

![The Add variable menu listing the eight variable types.](/images/item-templates/builder-add-variable-menu.png)

Each variable becomes a card with four things you can set:

![A variable card with its name, type, label and Required checkbox.](/images/item-templates/builder-variable-card.png)

| Setting | What it's for |
| --- | --- |
| **Name** | The internal handle, used in tokens (`{{Client}}`). Letters, numbers and underscores only, and unique within the template. |
| **Type** | What kind of answer this is. Determines which fields it can drive and what the person filling it in sees. |
| **Label** | The friendly prompt shown at apply time — "Client name", not "Client". Optional, but write one; it's what everyone else reads. |
| **Required** | Whether the apply is blocked until it's filled in. |

The ⓘ icon on each card shows where that variable is used — *"used in 1 title"*, *"not used yet"* — so you can spot a variable nobody wired up, or check what you'd break by deleting one.

A template can have up to **20 variables**.

## The eight types

| Type | The person applying is asked for | Fields it can drive |
| --- | --- | --- |
| **Text** | A line of text | Titles, descriptions |
| **Number** | A number | Titles, descriptions |
| **Date** | A calendar date | Start date, due date, titles, descriptions |
| **Options** | A choice from a list you define | Titles, descriptions |
| **User** | A person | Assignee |
| **Team** | A team | Team |
| **Board** | A board or cycle | Board placement |
| **Custom field** | A value for one of your organization's custom fields | That custom field |

They split into two families, and the difference matters.

**Text, Number, Date and Options** resolve to *text*, so they can be dropped into titles and descriptions as `{{tokens}}`.

**User, Team, Board and Custom field** are references to real records. They can't be written into a title — you attach them to a field by switching that field to **Variable** mode and picking the variable from the dropdown.

::alert{type="info" title="Options is a choice list"}
An **Options** variable holds a fixed list of answers — "Region: EMEA / AMER / APAC", say — with between 2 and 50 entries. Use it instead of Text when there are only a handful of valid answers, so nobody has to remember the exact spelling.
::

## Using a variable in a title or description

Switch the field's toggle from **Fixed** to **Variable**. An **Insert** dropdown appears listing every variable that can go in text.

![The Insert menu offering the {{Client}} (Text) token for the title.](/images/item-templates/builder-insert-variable-token.png)

Pick one and the token is inserted at the cursor. You can type around it freely — `{{Client}} onboarding`, `Kickoff workshop with {{Client}}`, `Q{{quarter}} planning for {{team_name}}` — and mix several tokens in one title.

::alert{type="warning" title="Fixed mode does not substitute"}
A `{{token}}` typed into a field that's still set to **Fixed** is treated as literal text — you'd get an item genuinely called "{{Client}} onboarding". If a token isn't resolving, check the toggle first.
::

Values inserted into rich-text descriptions are escaped, so a client name containing an angle bracket can't break the formatting.

## Using a variable on a field

For dates, assignees, teams, boards and custom fields, there's no token — you point the field at the variable directly.

Switch the field to **Variable** and choose the variable from the dropdown. The dropdown only offers variables of the matching type: a start date can only be driven by a **Date** variable, an assignee only by a **User** variable, and so on.

### Dates: one anchor, many offsets

Date variables are the most powerful thing in the builder, because a date field wired to a variable also takes a **day offset**.

Instead of asking for a date on every node, you ask for **one** anchor date and express everything else relative to it:

| Node | Start | Due |
| --- | --- | --- |
| Launch workstream | `launch_date` − 84 days | `launch_date` + 14 days |
| Discovery epic | `launch_date` − 84 days | `launch_date` − 42 days |
| Build epic | `launch_date` − 42 days | `launch_date` − 7 days |

Ask for the launch date once and the entire schedule places itself. Move the launch date, and everything moves with it — which is exactly what happens when you apply the same template next quarter with a different date.

The **Timeline** view in the structure pane draws this relative schedule so you can check the shape before any real dates exist.

![The Timeline view showing nodes plotted on an axis of days from the launch_date variable.](/images/item-templates/builder-timeline-view.png)

### User variables and scope

A **User** variable can be **scoped**, so the person picker at apply time doesn't offer your entire organization:

- **No scope** — anyone in the organization.
- **Scoped to a fixed team** — only members of a team you choose now.
- **Scoped to a team variable** — only members of whichever team was chosen in *another* variable on this same template.

The last one is the useful one. Ask "which delivery team?" first, then "who's the product lead?" and only offer people from that team. The builder shows this on the card as **Scoped to `{{delivery_team}}` — filled before this one**, and the apply dialog automatically asks the questions in the right order.

### Board variables

A **Board** variable asks for a board at apply time. A cycle counts as a board here, so it's a way to say "ask me which cycle this batch of work should go on".

If instead you want "whatever cycle is current when this is applied", don't use a variable — use the field's **Cycle** mode, which resolves against a cadence rather than asking a question. See [Building a template](/major-modules/item-templates/building-a-template#board-placement).

## What people see at apply time

Everything above shows up as a simple form. Variables appear in order, required ones are marked, and each shows the **label** you wrote:

![The apply dialog asking for the template's variables.](/images/item-templates/apply-step2-variables.png)

The person applying never sees tokens, node keys or types — just the questions. That's why the labels are worth writing carefully.

## Turning variables off

If a template turned out not to need its variables — or you inherited one that's more complicated than the job deserves — the **Variables** switch in the builder takes them out.

Switching it off on a template that already uses variables is **an edit, not a view change**, so it asks first and counts exactly what it's about to remove:

![The Turn variables off? dialog, counting the variables and the tokenised titles it is about to remove.](/images/item-templates/builder-remove-variables-confirm.png)

> *1 variable is removed. 2 titles or descriptions lose their tokens. Fixed values you have already set are kept. Nothing is saved until you press Save Template.*

The counts are of that template, so the sentence changes each time — a template with fields wired to variables also reports how many of those will be cleared.

Confirming does three things:

1. **Every variable is deleted** from the roster.
2. **Every field wired to one is cleared** — a variable start date, assignee, team or custom field goes back to unset, and a variable board placement becomes **None**. There's nothing to convert them into: a question and an answer aren't the same thing.
3. **Every `{{token}}` is removed** from titles and descriptions, and the gap it leaves is closed up. `{{Client}} onboarding` becomes `onboarding`.

Everything you set as a **fixed** value survives untouched — titles, dates, teams, priorities, tags, fixed custom-field values.

![The same template after the removal: two panes, no toggles, and titles left reading "onboarding" and "Kickoff workshop with".](/images/item-templates/builder-variables-removed.png)

::alert{type="warning" title="Rewrite the titles a token came out of"}
Removing a token leaves grammatical wreckage behind, exactly as above: `{{Client}} onboarding` becomes `onboarding`, and `Kickoff workshop with {{Client}}` becomes `Kickoff workshop with`. That is deliberate — leaving the braces in place would create an item genuinely called "Kickoff workshop with {{Client}}" — but it does mean you should read back over the affected titles afterwards and write them properly before saving.
::

Nothing is written until you press **Save Template**, so **Cancel** still walks away from the whole thing. Once saved, though, the removal isn't undoable — if the template is one other people rely on, [duplicate it](/major-modules/item-templates/overview#where-templates-live) and simplify the copy.

Switching the toggle back **on** just brings the panel and the toggles back. It doesn't restore anything that was removed and saved.

## Practical advice

- **Start with everything fixed, then promote.** Build the template concretely, apply it once in your head, and turn into variables only the fields you found yourself wanting to change.
- **One date anchor beats six date questions.** Ask for the milestone that everyone actually knows and offset from it.
- **Mark a variable Required only when the apply is genuinely wrong without it.** A blank optional variable just leaves the field empty; a blank required one stops the whole apply.
- **Label everything.** `product_lead` is for you. *"Who is leading this launch?"* is for everyone else.
- **Check the usage icon before deleting.** It tells you how many nodes depend on that variable.
