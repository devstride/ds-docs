The builder is where a template takes shape. Open it from **Templates → New Template**, or from **Edit** on any template row.

![The template builder with the structure tree, the node inspector and the variables panel.](/images/item-templates/builder-three-panes.png)

## The layout

The builder is up to three panes plus a header, and each pane answers a different question.

| Pane | Question it answers |
| --- | --- |
| **Structure** (left) | What items will exist, and how are they nested? |
| **Node** (middle) | What does *this one* item look like? |
| **Variables** (right) | What will the template ask for when it's used? |

The third pane only appears when the template uses variables — see [Simple mode](#simple-mode) below.

The header carries the template's **name**, **description**, its **audience** badge (with a **Share…** button once saved) and **Applies to** — the kinds of parent that will accept this template, derived automatically from the root node's type.

At the bottom: a save-state indicator, **Cancel**, **Preview** and **Save Template**.

## Simple mode

Not every template needs to ask anything. A standing checklist — the same five stories, every sprint retro, every new starter — is just a fixed shape you want to stamp out. For those, the variable system is machinery you have to learn your way past to get to the part you wanted.

The **Variables** switch, in the bar above the panes next to **Try it**, turns that machinery off.

![The builder in simple mode: two panes, no variables roster, and a node inspector with no Fixed/Variable toggles.](/images/item-templates/builder-simple-mode.png)

With it **off**, the builder is two panes instead of three:

- the **Variables** pane is gone
- every **Fixed / Variable** toggle is gone — title, description, start and due date, team, assignee, custom fields
- the **Insert** menus for placing tokens in text are gone

What's left is a plain form: a title, a description, some dates, a person. Nothing to fill in when the template is applied, and the apply dialog skips its questions step entirely.

**A new template starts in simple mode**, because most don't need more. Turn the switch on the moment you want the template to ask something, and the roster and the toggles come back exactly as described below.

::alert{type="note" title="The switch is not a setting you have to remember"}
There is no hidden "simple" flag stored on the template. A template is simple precisely when it has **no variables**, so the switch reflects the template rather than overriding it — reopen a template with variables and it opens with them on, every time. That's also why turning the switch *off* on a template that already uses variables is a real edit, and asks first: see [Turning variables off](/major-modules/item-templates/variables#turning-variables-off).
::

## Step 1 — Name it

Give the template a name and a description before anything else. The description is what everyone else reads in the apply picker when they're deciding whether this is the right template, so write it for them, not for you: *what job is this for, and when should someone reach for it?*

Template names must be unique among your own templates.

## Step 2 — Add the root

A new template is empty — an empty structure pane and nothing selected in the node pane. It also opens in simple mode, so there's no variables pane until you ask for one.

![The builder for a brand-new template, with its panes empty.](/images/item-templates/builder-new-empty.png)

Click the **+** button under the structure pane and pick what the template starts with.

![The Add root menu offering Workstream and every work type in the organization.](/images/item-templates/builder-add-root-menu.png)

You can start with a **Workstream**, or with any work type your organization has configured — Enterprise, Epic, Feature, Story, Task, and so on. That choice sets the template's root type and therefore where it can be applied later.

::alert{type="note" title="Roots must be the same kind"}
A template can have more than one root — use **+ Add sibling** at the bottom of the tree. But all roots must be the same kind: either every root is a workstream, or every root is a work item. You can't mix the two in one template.
::

## Step 3 — Build out the tree

Each node in the tree has four controls on the right:

- **+** — add a child under this node
- **⧉** — duplicate this node *and everything beneath it*
- **−** — remove this node and its subtree
- **☰ N** — how many fields are set on this node (click it to jump into the inspector)

Nodes can also be dragged by the handle on the left to reorder or re-parent them.

When you click **+**, the menu only offers work types that are **legal children** of that node in your organization's work-type hierarchy. Under a Workstream you'll see the full set; under an Epic you may see only Feature.

![The Add child menu under a Workstream, colour-coded and indented to match the work-type hierarchy.](/images/item-templates/builder-add-child-menu.png)

![Under an Epic the same menu offers only Feature and Sub-item, because those are the legal children.](/images/item-templates/builder-add-child-epic-menu.png)

The menu is colour-coded and indented to match your work-type tree, so you can see at a glance where a type sits.

::alert{type="tip" title="Sub-items are there too"}
Work-item nodes can also take **Sub-item** children — the same lightweight checklist items you'd add to a real work item. They appear at the bottom of the add-child menu.
::

**Size limits:** a template can hold up to **500 nodes**, nested up to **10 levels** deep, with up to **20 variables**.

## Step 4 — Fill in each node

Select a node and the middle pane becomes its inspector. A workstream node offers title, description, start date, due date and colour. A work-item node offers considerably more:

![The node inspector for an Epic, showing title, description, dates, team, assignee and board mode.](/images/item-templates/builder-work-item-inspector.png)

- **Title** and **Description** (rich text)
- **Start date** and **Due date**
- **Team** and **Assignee**
- **Board** — where the created item lands
- **Priority**, **Tags**, **Point effort**
- **Custom fields** — only the ones your organization has configured for *that work type*, so an Epic inspector shows the Epic's fields and nothing else

### Fixed or Variable

With the **Variables** switch on, most fields have a **Fixed / Variable** toggle beside the label. This is the single most important control in the builder:

- **Fixed** — the same value every single time the template is applied. Good for things that genuinely never change: a standard epic title, a boilerplate description, a default priority.
- **Variable** — the template *asks* for the value at apply time. Good for anything that changes per use: the client name, the launch date, who's leading it.

![The title switched to Variable mode, with an Insert menu for choosing which variable to place in the text.](/images/item-templates/builder-title-variable-mode.png)

[Variables](/major-modules/item-templates/variables) covers this in full. In simple mode the toggle isn't there at all — every field is fixed, which is the whole point of that mode.

### Board placement

The **Board** field has four modes rather than two, because "where does this land" has more than one sensible answer:

| Mode | Behaviour |
| --- | --- |
| **None** | The item is created without a board. Someone places it later. |
| **Fixed** | Always the same named board. |
| **Variable** | The template asks which board at apply time. |
| **Cycle** | Pick a board *folder* (a cadence) and an offset, and the item lands on whichever cycle of that cadence is current when the template is applied — plus or minus the offset. |

**Cycle** mode is what makes a template survive time. A template that says "the next cycle after the current one" keeps working next quarter; one that names a specific cycle goes stale the moment that cycle closes.

Board is also the one field that **keeps its toggle in simple mode** — minus the **Variable** option, leaving None, Fixed and Cycle. All three are placements the template decides for itself, so there's still a real choice to make; the other fields lose their toggle entirely because "Fixed" would be the only thing left on it.

![Board set to Cycle mode, with the builder flagging that the cadence still needs choosing.](/images/item-templates/builder-board-cycle-mode.png)

## Three ways to see the structure

The structure pane has three views, toggled at its top-left.

**Tree** is the default and is best for building — it shows nesting and gives you the per-node controls.

**Fields** turns the same nodes into a spreadsheet: one row per node, one column per field. Use it to sweep across the whole template and spot the node where you forgot the due date.

![The Fields view showing every node as a row with its fields as columns.](/images/item-templates/builder-fields-view.png)

**Timeline** appears once dates are wired to a date variable. It draws the template as a relative Gantt — an axis measured in *days from* the anchor date rather than in calendar dates, so you can see the shape of the schedule before any real dates exist.

![The Timeline view showing nodes plotted on an axis of days from the launch_date variable.](/images/item-templates/builder-timeline-view.png)

## Step 5 — Fix the problems

The builder validates as you type. If anything would stop the template working, a red **problems** badge appears above the panes; hover it to see each problem and which node it belongs to.

![The problems badge expanded, naming the node and the field that needs attention.](/images/item-templates/builder-problems.png)

Typical problems are an incomplete field (Cycle mode with no cadence chosen), a variable referenced by a node but since deleted, or a reference to a work type or team that no longer exists. **Save Template** stays disabled until they're resolved.

## Step 6 — Try it before you save

**Try it**, in the top right, opens the playground: a simulation of what an apply would create, side by side with the questions the template asks.

![The Try it playground showing the simulated result and the fill-in-the-values panel.](/images/item-templates/builder-playground.png)

Type a value and the simulated tree updates live — titles resolve, tokens disappear, dates shift.

![The same playground with the Client name filled in, showing titles resolved to Northwind Bank.](/images/item-templates/builder-playground-filled.png)

Nothing is created. Nothing is saved. The **Simulated** badge is there to make that unmistakable. **Sample values** fills every variable with a plausible value in one click so you can eyeball the whole shape immediately, and **Clear** empties them again.

In simple mode there's nothing to fill in, so **Try it** is purely a preview — the finished list of items exactly as an apply would create them.

::alert{type="tip" title="An empty variable is not an error"}
If you leave a variable blank in the playground, any title using it keeps showing the raw `{{token}}` — and the playground tells you so. That's honest: it is exactly what a real apply would produce. It's only an error if the variable is marked **Required**, which blocks the apply instead.
::

## Step 7 — Save

**Save Template** writes it. A new template is **private to you** until you share it — see [Sharing templates](/major-modules/item-templates/sharing-templates).

**Preview**, next to Save, is the other button worth knowing: it opens the real [apply dialog](/major-modules/item-templates/applying-a-template) with this template pre-selected, so you can walk the actual flow — target, values, preview — without leaving the builder.

## A worked example

This is a real template with four variables, showing most of the ideas above at once:

![A fully built template with four variables, a variable title, and dates anchored to a launch date with day offsets.](/images/item-templates/builder-real-template.png)

Reading it:

- The workstream's **title** is in Variable mode: `{{product_name}} Launch`.
- Its **start date** is `launch_date` **− 84 days** and its **due date** is `launch_date` **+ 14 days** — so the whole plan rebases around whatever launch date you type.
- `product_lead` is a **User** variable **scoped to** `{{delivery_team}}`, so the person picker only offers members of the team chosen one question earlier.
- Eleven nodes — a workstream, an epic, three features and six stories — all created in one apply.
