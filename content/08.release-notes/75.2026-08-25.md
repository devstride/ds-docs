## 🎚️ Delivery profiles: choose how much rigor the loop spends

When I released the delivery loop, it ran every item at the rigor we use on DevStride itself —
fine-grained stories, deep specs, a wide adversarial review, and a second local reviewer re-checking
every fix. That is right for a revenue-bearing product. It is wrong for a greenfield one: a team
validating a brand-new idea ran the loop at that setting and measured hours per story, most of it
spent reviewing code that had no users yet.

Version **0.10.0** makes rigor a choice instead of a constant. A **delivery profile** is one word —
`prototype`, `standard`, or `enterprise` — that moves the loop's knobs together: how finely a plan is
sliced, how deep each item's spec goes, how wide the adversarial review fans out, how many local
review rounds run, and which local checks gate a merge. Coarse items with an enterprise-grade review
fan-out is the most expensive combination there is, which is why this is one setting and not ten.

- **`prototype`** — rails and guidance, fast. One item per vertical slice a user can see, short
  specs, a narrow review, no second local reviewer, and the release unit merges on its own when its
  last item lands.
- **`standard`** — the middle a working product wants, and the new default.
- **`enterprise`** — high resolution, minimum exposure to error: the rigor the loop ran at before.

Some floors never move, whatever the profile: one maximum-effort adversarial Claude pass on every
item, the security lens whenever a diff touches an auth boundary, a green local gate before any
merge, and every configured cloud reviewer plus CI over the full diff at the release pull request.

## 🔀 Rebalance a plan that is already running

A plan sliced for `enterprise` that turns out to need `prototype` no longer has to be rebuilt.
`/devstride:rebalance I1234 prototype` re-slices the items that have not started, shows you a
before/after table, and changes nothing until you sign off. Done and In Progress items are untouched;
absorbed items are archived with a pointer to their successor, never deleted; dependencies are
rewired, execution-order numbers stay stable, and the timeline is re-dated. It is the eighteenth
skill.

## ⏱️ A review loop that is bounded by design

Two changes make a run's duration predictable:

- **Local review rounds are capped per profile** — none, one, or two runs of the local CLI
  reviewer per item. Past the cap, remaining findings are fixed without another re-review, and
  anything that is not a P1 or security finding is deferred with a written rationale instead of
  being re-litigated. A finding counts as refuted unless it can be reproduced.
- **Cloud reviewer waits fail fast.** A reviewer request must be proven registered on the pull
  request within two minutes, or that reviewer is dropped for the run and reported. The poll timeout
  now bounds only the wait for a reviewer that really was asked, and its default follows the
  profile: 5, 10, or 20 minutes.

## What to do

Update the plugin and restart Claude Code:

```bash
claude plugin marketplace update devstride
claude plugin update devstride@devstride
```

Then run `/devstride:setup` in each repository to pick a profile; it writes `"profile"` and matching
defaults into `.claude/ds-config.json`. A plan can also carry its own profile —
`/devstride:plan I1234 prototype` — and that wins over the repository setting for that plan.

::alert{type="warning" title="Existing configurations now run standard"}
A config without a `profile` key runs `standard`, which is lighter than the loop was before. To keep
the previous behaviour exactly, add `"profile": "enterprise"` to `.claude/ds-config.json`. Any
explicit key already in the file — auto-release, fast merges, the poll timeout, the CI-ordering
flags — still wins over whatever the profile would choose, and a configured local CLI reviewer
still reviews every pull request under every profile.
::
