::alert{type="warning" title="Read the update steps first"}
This release changes **how you get releases**. Plugins installed before 1.2.0 cannot tell they are behind and cannot update themselves, so every machine has to be brought forward **once, by hand** — after that the plugin does it for you. Five minutes per machine; the steps are below.
::

## ⬆️ Update first — once per machine, then never again by hand

**1. See what you have.** The update command needs the exact id and scope you installed under; guessing reports "not installed" and changes nothing.

```bash
claude plugin list
```

Note three things from the output: the id (`devstride@devstride`, or `ds@devstride` if you installed through the short alias), the scope (`user` unless you passed `--scope project`), and the version.

**2. Update — both commands, then restart.** The first refreshes the catalogue, the second upgrades your copy; running only the first reports success and leaves you exactly where you were.

```bash
claude plugin marketplace update devstride
claude plugin update devstride@devstride        # or ds@devstride — the id from step 1
                                                # add --scope project if that is where you installed
```

Restart Claude Code. A running session keeps serving the version it loaded at startup, so nothing changes until you do.

**3. Check the machine.** `/devstride:doctor` is read-only and reports every dependency with the command that fixes it: the plugin version on disk and in this session, the marketplace registration, git with a GitHub `origin`, `gh` installed *and signed in* with the `repo` and `read:org` scopes (`workflow` too if setup will edit your workflows), the DevStride connection, your `.claude/ds-config.json`, the CI draft gate, and the documentation hooks. If DevStride shows as not connected, run `/mcp` and connect **`plugin:devstride:devstride`** — until you sign in the skills have no DevStride tools at all, and nothing prompts you.

**4. Bring the repository forward — once per repository, not per machine.** Each of these proposes diffs you accept one at a time and preserves your hand edits and every `_`-prefixed annotation:

- `/devstride:setup docs` — asks where your documentation lives, how it is updated and how release notes are pushed, then **scaffolds two skills in your repository** (`.claude/skills/<update-documentation>` and `<update-release-notes>`) and points config at them. Say "none" if you have no docs site; the release skill then runs without a docs pass. If you have the retired `release.docsRepo` block, this migrates it.
- `/devstride:setup ci` — applies the run-once CI mechanics to your workflows (draft gate, per-PR concurrency, tree-identical skip on production pushes, the draft-convention check).
- `/devstride:setup` — describes your local environment (`localEnvironment`) and, if you want the plugin to apply releases for you, sets `plugin.autoUpdate`.

Commit what it writes — the config and the scaffolded skills are shared with your team through the repository, which is the point.

**5. Turn on auto-update.** Two ways, pick either: in Claude Code open `/plugin`, select the devstride marketplace and choose **Enable auto-update**; or set `plugin.autoUpdate: true` in `.claude/ds-config.json`, and the plugin applies a newer release at session start and asks you to restart. Either way, from 1.2.0 on every session start compares what it is running against the newest release and — only when you are behind — prints the two exact commands with the id it found. A team that needs to hold a version mid-incident sets `plugin.pin`; the check then reports the pin and never nags.

::alert{type="info" title="Teammates"}
A repository's `.claude/settings.json` registers the marketplace and enables the plugin — it does **not** install it. Every teammate runs `claude plugin install <id>` once on their own machine, then steps 1–3 above. `/devstride:doctor` prints the right id from the repository's own settings.
::

## 🩺 What every machine needs, and how you know

The delivery loop assumes a small, fixed set of tools, and `/devstride:doctor` now checks all of them without writing anything: **git** with an `origin` remote on GitHub; the **`gh` CLI**, installed and authenticated with `repo` and `read:org` (the one people miss — an installed `gh` looks like a working one); the **DevStride connection** through the bundled MCP server; the repository's **`.claude/ds-config.json`**; and, if your config names a local review CLI, that its binary resolves. Cloud review (GitHub Copilot) needs Copilot code review enabled for your GitHub organization. Anything missing is reported with its fix, and a configured engine that fails is reported as a degradation of that run — never silently equated with "not configured".

## 🔔 The plugin tells you when it is behind (1.2.0)

Versions used to drift silently between machines — an installed plugin stays at its version until someone updates it, and nothing in a repository says so. Now, at every session start, the plugin compares the version the session is running against the newest release and, **only when you are behind**, prints the two exact update commands with the installed id it found. It is silent when you are current or offline, never blocks or fails a session, and caps every network call. A repository can opt in to applying the update at session start (you are asked to restart), or hold a version deliberately with a pin that is reported once and never nags. `/devstride:doctor` shows when the check last ran. The mechanism was proven on observed behaviour before it was built: a scratch plugin's SessionStart hook fires in headless sessions, reaches the network in about 300 ms, and does not block a session even when it fails.

## 📝 Release notes are yours to ask for — never the loop's to decide (1.0.0)

The release skill used to judge for itself whether a release "deserved" a note and publish one. It guessed wrong, in public, on a release whose owner had said no. Version 1.0.0 ends that: a release note is written only when you pass `--release-notes` to `/devstride:release` — `true` to publish, `draft` to read it first — and only after the production merge is confirmed and the deploy verified live. Nothing in the loop interprets "large" or "user-facing" on your behalf.

## 🧩 Documentation through skills your repository owns (1.0.0)

The plugin no longer edits documentation itself — it could not know where yours lives. `/devstride:setup docs` asks three questions, scaffolds two local skills in your repository with the answers, and writes only their names into `.claude/ds-config.json` (`docs.updateSkill`, `docs.releaseNotesSkill`). A production release hands them a structured delta — every item in plain English, with a `live` flag that is true only once the deploy is confirmed — and the skill decides what "publish" means for you: a push, a pull request, a hand-off. Core documentation is updated by default (`no docs` suppresses it); release notes only on the flag. `/devstride:doctor docs` checks both hooks without writing anything.

::alert{type="warning" title="release.docsRepo is retired"}
1.0.0 is a major bump because an existing key changed meaning: the release skill no longer acts on `release.docsRepo`. Run `/devstride:setup docs` once — it migrates the block into a local skill and removes it. Until then the release skill reports the legacy shape and runs without docs.
::

## 💸 CI that runs once — measured, not assumed (1.1.0)

Version 1.1.0 starts from a measurement. The draft hold already made CI run once per pull request; auditing one repository showed the rest of the bill lived elsewhere — half the test minutes were post-merge runs on the production branch re-testing the exact tree the base branch had just tested, and a release pull request re-ran every time something merged beneath it.

- **`/devstride:ci-audit`** — counts executed runs and minutes (never raw run counts, which the Actions usage page inflates with skipped draft runs), classifies them, and names the offenders with their likely cause. The design number is executed runs per pull request per workflow = 1.
- **`/devstride:setup ci`** — applies four workflow mechanics as diffs you accept one by one: the draft gate, per-pull-request `concurrency` that cancels a superseded run, a tree-identical skip on production-branch pushes, and a check that fails a non-draft pull request a person opens with the convention in the message. It is the only path by which setup ever touches a workflow. On DevStride's own repository the first production push after this release finished every workflow in under a minute with the heavy jobs skipped.
- **The release source is frozen while a release is ready.** `release` merges or parks every ready pull request into it before cutting and re-validates the reviewed head before the flip; `build-item` waits rather than merge beneath a ready release pull request. `review` reports "N executed CI runs on this pull request" at close-out. Both rules are on by default.

## 🖥️ Local environments, described once (1.2.0)

The loop no longer assumes every repository has exactly one working tree and one database. A new `localEnvironment` block in `.claude/ds-config.json` describes how a repository stands up an isolated local instance — create, seed, migrate, tear down, and whether an instance belongs to a directory or a branch. `/devstride:setup` gathers candidates and asks rather than guessing; `/devstride:doctor` reports the block; the hotfix skill runs the migrate and seed commands from it instead of asking every time. The serial-execution rule is restated against what actually constrains it — shared test infrastructure and production writes — so per-checkout instances are supported without being mistaken for a licence to run builds in parallel.

## 🔍 Verification names its path (1.2.0)

When a review verdict rests on having looked — a browser, a running service, a manual run — it now reports "verified X via path Y" and lists the routes to the same state that were not tried. A fix confirmed on one path proves nothing about the others, and this rule was written after exactly that: a UI fix passed every automated gate, was confirmed by opening the link, and shipped with a hole on two routes nobody had named. The review engine's tests lens now looks for the pattern.
