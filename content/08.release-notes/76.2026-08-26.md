## 📝 Release notes are yours to ask for — never the loop's to decide

The release skill used to judge for itself whether a release "deserved" a note and publish one. It
guessed wrong, in public, on a release whose owner had said no. Version **1.0.0** ends that: a
release note is written only when you pass `--release-notes` to `/devstride:release` — `true` to
publish, `draft` to read it first — and only after the production merge is confirmed and the
deploy verified live. Nothing in the loop interprets "large" or "user-facing" on your behalf.

## 🧩 Documentation through skills your repository owns

The plugin no longer edits documentation itself — it could not know where yours lives. Instead
`/devstride:setup docs` asks three questions (where documentation lives, how it is updated, how
release notes are pushed), scaffolds two local skills in your repository with the answers, and
writes only their names into `.claude/ds-config.json` (`docs.updateSkill`,
`docs.releaseNotesSkill`). A production release hands them a structured delta — every item in plain
English, with a `live` flag that is true only once the deploy is confirmed — and the skill decides
what "publish" means for you: a push, a pull request, a hand-off. Core documentation is updated by
default (`no docs` suppresses it); release notes only on the flag. `/devstride:doctor docs` checks
both hooks without writing anything.

::alert{type="warning" title="release.docsRepo is retired"}
Version 1.0.0 is a major bump because an existing key changed meaning: the release skill no longer
acts on `release.docsRepo`. Run `/devstride:setup docs` once — it migrates the block into a local
skill and removes it. Until then the release skill reports the legacy shape and runs without docs.
::

## 💸 CI that runs once — measured, not assumed

Version **1.1.0** starts from a measurement. The draft hold already made CI run once per pull
request; auditing one repository showed the rest of the bill lived elsewhere — half the test minutes
were post-merge runs on the production branch re-testing the exact tree the base branch had just
tested, and a release pull request re-ran every time something merged beneath it.

- **`/devstride:ci-audit`** — counts executed runs and minutes (never raw run counts, which the
  Actions usage page inflates with skipped draft runs), classifies them, and names the offenders
  with their likely cause. The design number is executed runs per pull request = 1.
- **`/devstride:setup ci`** — applies four workflow mechanics as diffs you accept one by one: the
  draft gate, per-pull-request `concurrency` that cancels a superseded run, a tree-identical skip
  on production-branch pushes, and a check that fails a non-draft pull request a person opens with
  the convention in the message. It is the only path by which setup ever touches a workflow.
- **The release source is frozen while a release is ready.** `release` merges or parks every ready
  pull request into it before cutting and re-validates the reviewed head before the flip;
  `build-item` waits rather than merge beneath a ready release pull request. `review` reports
  "N executed CI runs on this pull request" at close-out. Both rules are on by default.

## 🖥️ Local environments, described once (1.2.0)

The loop no longer assumes every repository has exactly one working tree and one database. A new
`localEnvironment` block in `.claude/ds-config.json` describes how a repository stands up an
isolated local instance — create, seed, migrate, tear down, and whether an instance belongs to a
directory or a branch. `/devstride:setup` gathers candidates and asks rather than guessing;
`/devstride:doctor` reports the block; the hotfix skill runs the migrate and seed commands from it
instead of asking every time. The serial-execution rule is restated against what actually
constrains it — shared test infrastructure and production writes — so per-checkout instances are
supported without being mistaken for a licence to run builds in parallel.

## 🔍 Verification names its path

When a review verdict rests on having looked — a browser, a running service, a manual run — it now
reports "verified X via path Y" and lists the routes to the same state that were not tried. A fix
confirmed on one path proves nothing about the others, and this rule was written after exactly
that: a UI fix passed every automated gate, was confirmed by opening the link, and shipped with a
hole on two routes nobody had named. The review engine's tests lens now looks for the pattern.

## 🔔 The plugin tells you when it is behind

Versions used to drift silently between machines — an installed plugin stays at its version until
someone updates it, and nothing in a repository says so. Now, at every session start, the plugin
compares the version the session is running against the newest release and, **only when you are
behind**, prints the two exact update commands with the installed id it found. It is silent when
you are current or offline, never blocks or fails a session, and caps every network call. A
repository can opt in to applying the update at session start (you are asked to restart), or hold
a version deliberately with a pin that is reported once and never nags. `/devstride:doctor` shows
when the check last ran. The mechanism was proven on observed behaviour before it was built: a
scratch plugin's SessionStart hook fires in headless sessions, reaches the network in about 300 ms,
and does not block a session even when it fails.

## What to do

Update the plugin and restart Claude Code:

```bash
claude plugin marketplace update devstride
claude plugin update devstride@devstride
```

Then, once per repository: `/devstride:setup docs` to register your documentation (or say it has
none), `/devstride:setup ci` to apply the CI mechanics, `/devstride:setup` to describe your local
environment, and `/devstride:doctor` to see all of it reported. Run `/devstride:ci-audit 7` in a
week to see the difference in minutes. From 1.2.0 on, the plugin itself will tell you the next time
you are behind.
